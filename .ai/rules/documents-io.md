# Documents IO

## DOCX/Markdown mapping is one contract, written twice

`App\Documents\Import\DocxImporter` and `App\Documents\Export\DocxExporter` are round-trip partners: what the exporter emits is exactly what the importer reads back, and `tests/Feature/Documents/ImportExportTest` asserts it. Change one side and you must change the other.

| Dot.Doc JSON | .docx (export) | back out (import) |
| --- | --- | --- |
| `heading` level 1-6 | `addTitle(TextRun, level)` with the `Heading{n}` paragraph style; the `Outline` number is prefixed as LITERAL text | `Title` -> `heading`; level from `Title::getDepth()`, depth 0 (Word's `Title` style) becomes level 1 |
| `bulletList` / `orderedList` (incl. NESTED) | one `addListItemRun($depth, DotDocBullet|DotDocNumber)` per item, a nested list at `$depth + 1` into the SAME container - Word has no nested list element, only a flat run of paragraphs each carrying its own `w:ilvl` | consecutive `ListItemRun`/`ListItem` rebuilt into ONE tree by that depth (`DocxImporter::buildLists()`): a deeper item becomes a nested list inside the previous item's content, whatever its own numbering says. At the list's own depth a different numbering key starts a new list |
| a `listItem`'s SECOND and later paragraphs | written into the run the item already opened, separated by an inline break - Word has no unnumbered continuation paragraph this writer can emit | one paragraph with a `hardBreak`. The text stays INSIDE the item (writing them as ordinary paragraphs instead detaches them from the list entirely); the paragraph BOUNDARY is the accepted loss |
| `table` | `addTable`, first row `['tblHeader' => true]`, header cells bold, header band / zebra fill from the style's `table` tokens | `Table` -> `table`; a `tblHeader` first row becomes `tableHeader` cells, every other row `tableCell` |
| `image` with a `/storage/...` src | `addImage()` ONLY after `DocxExporter::publicDiskPath()` says so: the src must match a plain path pattern (no `.`/`..` segment, an image extension) AND `realpath()` must still land under `realpath(Storage::disk('public')->path(''))`. Anything else - a remote src, a traversal src, a file type this app does not store - is SKIPPED, never fetched and never embedded | embedded picture written to `storage/app/public/documents/{uuid}/{sha1}.{ext}` and referenced as `/storage/documents/{uuid}/...`; only png/jpeg/gif/webp (sniffed, not trusted from the file name), max 5 MB each and 50 per document (`DocxImporter::MAX_IMAGE_BYTES`/`MAX_IMAGES`, constructor-overridable) - over either cap the picture is skipped and the rest of the document still imports |
| marks bold/italic/underline/strike/code/highlight/sub/superscript/textStyle colour/link | run font properties: `code` -> the `fonts.mono` token as the run's font name, `highlight` -> `fgColor` (Word's `w:highlight`, which is an enum - yellow, not the token colour; the `bgColor` this used to set is not written by PhpWord's font-style writer AT ALL), `textStyle` -> `w:color`; a http(s)/mailto link becomes `addLink` | SYMMETRIC - `DocxImporter::fontMarks()` reads every one of those back (mono-looking font name -> `code`, `fgColor`/`bgColor` -> `highlight`, `w:vertAlign` -> sub/superscript, `w:color` -> `textStyle`). `Link` -> a `link` mark, and a link run is read WITHOUT its colour (Word writes a hyperlink's blue as ordinary character formatting, so reading it back would stamp a `textStyle` onto every imported link) but WITH its underline, so a link run comes back with both `underline` and `link` |
| `hardBreak` | `addTextBreak()` inside the run, then `DocxExporter::reattachInlineBreaks()` rewrites the bare `<w:br/>` PhpWord emits as a `<w:p>`-level sibling into `<w:r><w:br/></w:r>` | inline `TextBreak` -> `hardBreak`; a block-level `TextBreak` is Word's empty paragraph, so it becomes an empty `paragraph`, not a stray break |
| `pageBreak` / `sectionBreak` | `addPageBreak()` (an empty paragraph inside a table cell, where PhpWord forbids `PageBreak`) | `PageBreak` -> `pageBreak`, and the break-only paragraph the reader echoes straight after it is swallowed |
| `toc` | `addTOC()` (a real Word field) | the field paragraph comes back as a `PreserveText` holding `{TOC \o 1-3 ...}` -> one `toc` node, and the entry paragraphs Word caches inside the field are SWALLOWED |
| `callout` / `blockquote` / `codeBlock` / `columns` / `figure`+`caption` | shaded / indented / mono paragraphs; a `columns` and a `figure` write their children straight into the section | shape is lost, CONTENT IS NOT; they come back as paragraphs (and a figure's picture as a loose `image`) |
| anything else | - | unknown element -> a paragraph of its plain text |

Two known import limitations, both accepted rather than fixed. A foreign `.docx` with several `w:sect`s FLATTENS: every section's elements are appended in order with no `sectionBreak` between them, so a multi-section file loses its section boundaries (this app's own export writes exactly one section, so the round trip that matters is unaffected). And `sectionBreak`'s `attrs.setup` (landscape, a different paper size) is INERT on DOCX export exactly as it already is on the PDF and HTML surfaces - a cross-cutting gap in the section model, not a DOCX one.

`DocxExporter::escape()` and `DocumentSchema::normalise()` both strip the C0 control characters XML forbids - normalise() on the way IN (so importers, the autosave endpoint and legacy blobs cannot store one) and escape() on the way OUT for content stored before that. Neither pattern carries `/u`: every byte matched is ASCII, and a unicode pattern returns null - losing the whole string - the moment the text is not valid UTF-8, which imported content sometimes is not.

`Style::resetStyles()` runs at the top of BOTH `DocxImporter::import()` and `DocxExporter::export()`. `PhpOffice\PhpWord\Style` is a process-wide static registry: the reader pushes each file's numbering definitions into it as `PHPWordList{numId}`, and `setStyleValues()` keeps the FIRST definition of a name. Without the reset, a second import resolves its bullet-vs-number list types against the first document's numbering, and a second export writes the first document's heading fonts.

`addTitleStyle()` must run before any `addTitle()` - `PhpWord\Element\Title` only records its `Heading{n}` pStyle if that style is already registered, and with no pStyle nothing downstream (Word's navigation pane, its TOC field, `DocxImporter`) can tell the paragraph was a heading. `DocxExporter` passes a DETACHED `TextRun` to `addTitle()` rather than a string so a heading keeps its own marks; the Word2007 writer still resolves hyperlink relation ids for it, but an image added to such a run would never reach the media collection, so `writeImage()` refuses a container whose `getPhpWord()` is null.

PhpWord's TOC writer reads every registered `Title` back with `writeText($title->getText())` and TypeErrors (a 500 on the export route) when that text is a `TextRun`. So `DocxExporter` scans the document for a `toc` node up front and, when it finds one, writes plain-string headings instead of runs — losing a heading's own italic/link marks is the price of a working table of contents. Found by exporting the demo "Quarterly operations review", which has a `toc`.

Word has no linked numbering definition in what this writer emits, so a numbered heading's `Outline` number is written as literal text. That is deliberate: it keeps `crossRef` labels and heading numbers agreeing in the exported file. It is also the only difference a full export -> re-import round trip of a real document produces at the TEXT level: `DocumentSchema::plainText()` before and after differs by exactly the number prefixes ("Throughput" -> "1.1 Throughput"), and the block count is unchanged. Structurally the round trip is symmetric for headings and their levels, nested lists of either type, tables and their header row, images, every inline mark, hard breaks and the `toc`; what it does NOT return unchanged is the shape row above (`blockquote`/`callout`/`codeBlock`/`columns`/`figure` come back as paragraphs), a `taskList` (a bullet list with a literal `[x] ` prefix), and a multi-paragraph list item (one paragraph with a break).

## Every importer returns JSON that has already passed ensureIds + normalise

`DocxImporter`, `MarkdownImporter`, `PlainTextImporter` and `HtmlToJson` all end with `$schema->normalise($schema->ensureIds($doc))` and the result must pass `DocumentSchema::validate()` with no errors. This is a contract, not a convenience: `DocumentStore::save()` validates but does NOT repair, and the editor runs with `enableContentCheck: true`, so a single node ProseMirror's content expressions reject (an empty `<table>`, a `listItem` opening with a nested list) opens the whole imported document READ-ONLY with autosave off. See `.ai/rules/app.md`. Import sources are the messiest input this app takes, so a new importer that skips either call is a bug even when `validate()` happens to be happy.

`MarkdownImporter` is commonmark -> HTML -> `HtmlToJson` (with `html_input => strip` and `allow_unsafe_links => false`, because imported files are untrusted). `HtmlToJson` enforces the SAME scheme allow-list itself, because the `.html`/`.htm` path and every legacy blob reach it without going through commonmark: `HtmlToJson::safeUrl()` keeps only http/https/mailto (http/https for an `<img src>`) plus a root-relative `/...` or a `#fragment`, and an href that fails loses the ATTRIBUTE, never the text. It also reads commonmark's task-list markup (`<li><input type="checkbox">`) back as a `taskList` of `taskItem`s, which is what makes checkbox state survive a Markdown round trip.

`PlainTextImporter` is deliberately NOT routed through it: a .txt line starting `# ` or `* ` is not asking to become a heading or a bullet. `DocumentImportController` dispatches on the CLIENT extension (`docx, md, markdown, html, htm, txt`, max 20 MB) after `mimes:` has checked the sniffed type, and saves with `['version' => 'named', 'label' => 'Imported '.$originalName]`. It is rate limited at 10 imports per user per hour, the same budget the export route spends, and every importer call is wrapped: a file whose bytes sniff as a .docx but whose OOXML is broken reaches PhpWord as anything from its own exception to a DOMDocument warning promoted to an ErrorException, and all of it answers 422 ("This file could not be read."), never a 500.

## Markdown export walks the JSON, it does not convert HTML

`MarkdownExporter` does not render HTML and run it through `league/html-to-markdown`: that converter has no table handler (a document's tables come out as one run-on line of cell text) and the document-only nodes have no HTML shape it could recognise. It emits GFM pipe tables straight from the JSON - promoting the first row to the header row, since Markdown has no body-only table - ATX headings, fenced code, `crossRef` as its resolved LABEL (a .md file has nowhere to resolve a block id), `variable` as `{{ key }}`, and omits `toc` entirely rather than freezing a stale copy of the headings.

Three rules keep that output re-importable, and all three exist because a round trip broke without them:

- **Every literal text run is escaped.** `escapeInline()` escapes `\ ` `` ` `` `*` `_` `[` `]` `<` `|` anywhere in a line, and `escapeLineStart()` escapes what only means something in the first column (`#` `>` `+` `-`, `1.`/`1)`, and a line of nothing but `-`/`=`). Without it a paragraph reading `# not a heading` came back as a heading. Text inside a `code` mark is NOT escaped - a code span is literal - so its fence is instead grown longer than the longest backtick run it holds.
- **A plain bullet is `*`, a task item is `-`.** CommonMark ends one list and starts another when the bullet CHARACTER changes; sharing a marker merged a `bulletList` and the `taskList` after it into one list.
- **A list item's second and later blocks are separated by a BLANK line** as well as indented by the marker width. Without the blank line CommonMark's lazy continuation folds the second paragraph into the first.
