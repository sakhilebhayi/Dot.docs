# App

## All document content writes go through DocumentStore
Never write Document::content, content_json, search_text, word_count, or version directly (e.g. via ->update([...]) or ->save() after mutating those fields by hand). Always go through App\Documents\DocumentStore: create() for new documents, save() for edits (accepts Dot.Doc JSON, validates against DocumentSchema, renders HTML, updates search_text/word_count, and cuts a version per the auto/named/restore/none rule), restore() for version restores, restyle() for a style change, and refill() only from the one-off backfill command. Any writer that produces HTML (importers, AI suggestion acceptance, legacy content) must first convert it with App\Documents\Import\HtmlToJson::convert() and hand the resulting JSON to DocumentStore::save(). This keeps content, content_json, search_text, word_count, and version snapshots from drifting out of sync. Found drifting in DocumentImportController::store() and Editor::acceptSuggestion() during Task 4 review (fix round 1).

## DocumentSchema::normalise() repairs what ProseMirror's content expressions reject
`DocumentSchema::validate()` and ProseMirror's content expressions are NOT the same check. validate() is happy with an empty `<table>`, a `bulletList` with no items, a `listItem` that opens with a nested list, or a `columns` whose child count does not equal `attrs.count`; ProseMirror refuses all of them - and the editor is built with `enableContentCheck: true`, so ONE of them opens the whole document READ-ONLY with autosave off. `normalise()` therefore repairs as well as whitelists: it drops empty `table`/`tableRow`/`bulletList`/`orderedList`/`taskList`, gives an empty `listItem`/`taskItem`/`tableCell`/`tableHeader`/`blockquote`/`callout`/`column` (and an empty `doc`) a paragraph, prepends a paragraph to a `listItem`/`taskItem` that does not start with one, makes `columns` children match `count` (extras MERGE into the last column, never dropped; short ones are padded), and forces `figure` to `(image|table) caption` WITHOUT LOSING ANYTHING: the first media child and the first caption stay inside, and every other child is LIFTED OUT as a sibling immediately after the figure. A lifted child becomes a paragraph unless it is itself top-level-valid: `liftToBlock()` passes through anything already legal as a direct child of `doc`/`column` (both are `block+`) unchanged - `image`, a second `figure`, and so on - and converts everything else (`column`, `tableRow`, `tableCell`, `tableHeader`, `listItem`, `taskItem`, `caption` - content ProseMirror only allows inside one specific parent) into a paragraph of its own plain text (`DocumentSchema::plainText()`), keeping its own block id, dropped only when that text is empty. `enableContentCheck` would otherwise refuse a `column` or `tableRow` sitting bare at `doc`'s top level exactly as it refuses a stray `caption`. The same rule applies everywhere normalise() moves a node to a new parent, not just out of a figure - `normaliseColumns()` runs a `columns`-child that is not itself a `column` through `liftToBlock()` too before wrapping it into a synthetic column, since `column` is `block+` just like `doc`. A figure with no media at all cannot be a figure, so it is replaced by what it was holding rather than deleted with it. Keeping only the first two children silently deleted the writer's second picture. This is why `normaliseNode()` returns a LIST of nodes, not one node - a repair may expand into several - and why `normaliseChildren()` splices rather than appends. Nodes normalise() creates from nothing (an empty paragraph, a padded column) carry a fresh `BlockId::generate()`, because `validate()` runs after it; nodes `liftToBlock()` converts keep the id they already had, because `ensureIds()` (which runs before `normalise()` on every write path) already made it valid and document-unique. It is run by `DocumentStore::create()`/`save()` on the way in, by `HtmlToJson::convert()` (every legacy blob, importer and AI acceptance) and by `DocumentStore::json()` on the way OUT to the editor, which is what makes a document stored before these repairs existed still open editable. Guard `count($node['content'] ?? [])` against non-array content throughout: this data comes from importers and from the wire. The same goes for `attrs`: a block whose `attrs` arrived as a non-array scalar (e.g. a malformed autosave payload) must be treated as `[]` in both `ensureNodeIds()` and `normaliseNode()` - unguarded, `array_merge()`/`array_key_exists()` throw a TypeError (a 500) instead of leaving the input to fail `validate()` normally.

## The editor's beacon autosave is a controller, and it still writes through DocumentStore
`App\Http\Controllers\DocumentAutosaveController` (`POST /documents/{uuid}/autosave`, inside the `auth:sanctum` group) exists because Livewire cannot issue a request during page unload - its CommitBus defers every `$wire` call on a 5 ms timer the unloading page never runs - so the editor's last-chance flush uses `navigator.sendBeacon()`, which can only POST to a plain endpoint. It is not an exception to the "all content writes go through DocumentStore" rule above: it authorises `update`, validates that the body is a `doc`, calls `DocumentStore::save($doc, $json, $user, ['version' => 'none', 'expectedVersion' => base_version])` so no version snapshot is cut for someone merely navigating away (plus `keepReplacedAs` when the body says `overwrite: true` - see "A save states the version it was based on" below), translates the store's `InvalidArgumentException` into a 422 `ValidationException`, and returns `{version}`. It saves `$request->input('content')` - the RAW array - never `$request->validate()`'s return value: validate() gives back only the keys it was given rules for, so validating `content.type`/`content.content` and saving that stripped `content.attrs` (schema/style/vars) off every beacon save and let `ensureIds()` re-stamp the defaults, resetting the document's style and variables behind the writer's back. Rules on a nested document body are a SHAPE check only; `DocumentSchema::validate()` inside `DocumentStore::save()` is what vets the content. Anything else that needs to write content from a plain HTTP request follows the same shape.

## DocumentPolicy answers from the database every time - never cache an access decision
`DocumentPolicy::view()` and `update()` used to `Cache::remember()` their answer per user per document for 15 minutes (`doc.view.{user}.{doc}`, `doc.update.{user}.{doc}`), and nothing that changes access ever forgot those keys: a removed collaborator or team member kept opening the document, a demoted editor kept saving, and somebody refused once (e.g. opening a link before the invitation landed) stayed refused after being invited. `DocumentObserver` only busted the keys on DOCUMENT changes, and only for the owner and current collaborators. Do not bring the cache back with forget() calls at the mutation sites: access changes in `ShareManager::invite()`/`removeCollaborator()`, in Jetstream's own `TeamMemberManager` (add, remove, leave, role change - vendor code this app does not pass through), on team and user deletion, and when a document changes team; missing one is a silent authorization hole. The lookup is one indexed `exists()` query, and production's cache store is the same SQLite file, so the cache never saved a query anyway. `tests/Feature/Documents/DocumentAccessFreshnessTest.php` asks the policy before AND after each change, for: collaborator invite / remove / role change through `ShareManager`, and team add (the `AddsTeamMembers` action), remove, leave and role change through Jetstream's `TeamMemberManager`. Team deletion, user deletion and a document changing team are NOT exercised there. In a test, ask the second time with `$user->fresh()` and `$doc->fresh()`: `teamRole()` reads the `$team->users` relation already loaded on the model instance, so reusing the same objects tests PHP's memory, not the policy.

## A Livewire component that shows document content re-checks access in hydrate(), not only in mount()
`mount()` runs once, when the page is first opened; every later request from that open page skips it. `VersionHistory` and `CommentThread` used to authorize `view` in `mount()` alone (CommentThread not at all - it relied on the editor that embeds it), so somebody removed from a document could keep previewing versions and reading comments - including ones written after they were removed - for as long as the tab stayed open. Both now authorize in `hydrate()`. `Editor` gets the same effect from `outline()`, which its `render()` calls and which authorizes. A new component that renders anything of the document's on re-render needs the same hook; per-action `authorize()` calls only protect the actions. Do not put it in `boot()` (runs before `mount()`, when `$document` is not set yet), and check a `lazy` component before adding it: its placeholder round trip has no `$document` either. What this does NOT close: a presence-channel subscription is authorized once, at join, so an open editor keeps receiving `DocumentUpdated` broadcasts (which carry the whole document) until the tab is closed.

## A save states the version it was based on, and a stale one is refused
`DocumentStore::save()` takes `['expectedVersion' => int]`. When it is given and the stored document has moved on it throws `App\Documents\StaleDocumentException` (carrying `currentVersion`) and writes nothing. Both editor save paths state it: `Editor::saveContent($content, $baseVersion, $overwrite)` (returns `{ok, conflict, version}`; a null base is refused with a "reload" error, because it comes from a tab running old JavaScript, and THAT answer carries `version: null`, never the current version: the old JavaScript adopts any numeric `version` it is answered with as the base of its offline draft before it looks at `ok`, so handing it the current version made a draft built on an older one claim to be up to date, and the reload the message asks for restored it over everything saved since, passing the stale check - `EditorSaveBaseVersionTest::test_the_refusal_to_an_old_tab_does_not_hand_it_the_current_version`) and the unload beacon (`base_version`, answers 409 when stale). Before this, two people with a document open each replaced the other's work with a stale whole-document copy on every autosave, silently. Writers that replace the document on purpose - restore, import, an accepted suggestion - state no base and always go through; do not add `expectedVersion` to those. What they write is the content they were handed (the version row, the uploaded file, the suggestion), never the content of the model they pass. `save()` takes NOTHING from that model's copy of the document, which Livewire loaded when the request began and somebody else may have replaced since: inside the transaction it reads the whole ROW under the write lock (`lockStored()`: `lockForUpdate()`; SQLite's IMMEDIATE transaction mode takes the write lock on BEGIN), counts the new version as that row's `version + 1`, brings the passed model up to the row (`bringUpTo()`, keeping only what the caller itself changed on it) and only then fills it from the JSON. That last step matters because Eloquent writes only the columns that differ from what the model was loaded with: compared against a request-start copy, a column whose new value equalled the old copy's was skipped and kept the other person's value, so a restore of exactly the text the stale copy held raised the version and restored nothing, and a row could end up with one person's `content_json` and another's `search_text` (`DocumentStoreVersionGuardTest::test_a_save_from_a_model_loaded_earlier_still_writes_every_content_column`). A style change is NOT one of the replace-on-purpose writers and must not go through `save()`: it has no new content to hand over, so the only content it could pass is the model's own request-start copy, and `Editor::setStyle()` doing exactly that wrote the copy back over a save that landed between the request's hydration and its write. It calls `DocumentStore::restyle($doc, $styleKey)`, which locks and re-reads the row the same way, sets `style_key`, refills from the row's OWN stored content (renumbered and re-rendered under the new style), raises the version, cuts no version and fires the webhook after the commit (`tests/Feature/Documents/DocumentRestyleTest.php` lands a save inside the style change request and checks `content_json`, `content` and `search_text`). Anything new that re-derives stored content without changing it follows `restyle()`, not `save($doc, $doc->content_json, ...)`. The `on_save` webhook fires after the transaction commits: it is an HTTP call to somebody else's server and must not hold the write lock or announce a save that rolls back. `$overwrite` is the editor page's "Keep mine" or "Put it back" choice - a writer knowingly saving over a newer version that their base is on. The save that carries out that choice is the Livewire one (`$overwrite`) or, when the page is closed before it goes out, the unload beacon, so `DocumentAutosaveController` accepts the same statement: an optional boolean `overwrite` in the beacon's body. A beacon sent without it for such a save stores the writer's text over the newer version and keeps that version nowhere. The person who wrote that version is not asked and is not told, so both writers pass `['keepReplacedAs' => DocumentStore::overwriteLabel($user)]` ("Before <name> kept their version"; one helper, so the two cannot drift apart) and `DocumentStore::save()` cuts a `named` version of the STORED document with that label INSIDE the save's transaction, after the stale check: the replaced text must stay in the history, because the save that wrote it may have cut no version of its own. It is cut there and nowhere else. Cutting it from the component before calling `save()` ran outside the transaction and left a stray version behind every overwrite that was then refused (content the schema rejects, or a document that moved on in between). The three writers that state no base keep what they replace the same way, because they replace somebody's saved text without asking either, and every open tab then follows the replacement and loses its undo: `DocumentStore::restore()` passes `'Before restoring v<n>'`, `DocumentImportController` `'Before import of <file name>'` and `Editor::acceptSuggestion()` `'Before accepted suggestion'`. A new writer that replaces the document passes `keepReplacedAs` too. `save()` skips the cut when a version row with the stored version number already exists (`hasVersion()`): that text is in the history already. The skip is decided inside the transaction, about the row read under the lock, and must stay there: a writer that looked before calling `save()` would miss an autosave landing in between and replace a head that is in no row. So `keepReplacedAs` means "make sure the replaced text is in the history", not "always cut a row with this label". Covered by `tests/Feature/Documents/DocumentStoreVersionGuardTest.php` and `EditorSaveBaseVersionTest.php`; the three base-less writers each have a test that makes two same-author saves inside two minutes (so the head is in no row) and then runs the writer: `VersionHistoryTest`, `ImportRoutesWriteTest`, `EditorSuggestionsTest`. The beacon's `overwrite` is covered in `DocumentAutosaveTest` (kept with the flag, nothing kept without it, nothing kept when refused as stale).

## Presence is one row per open tab, refreshed by the sync poll
`App\Services\PresenceService` reads and writes `document_presences` (query builder, no model): `touch()` at most once every 5 seconds per tab, `leave()` on the unload beacon, `members()` for the strip (distinct users seen in the last 30 seconds) and `others()` (other live TABS, which is what decides how fast a tab polls - another tab of the same account counts). `touch()` writes with ONE `upsert` statement; `updateOrInsert()` is two (exists, then insert), and two requests for the same new tab arriving together would collide on the unique index. It replaced a single cache entry per document rewritten read-modify-write on a 60 second Livewire heartbeat, which lost concurrent updates and could not tell two tabs of one account apart. `App\Http\Controllers\DocumentSyncController` is the only writer. A quiet poll there selects six small columns of `documents` and never the content - `DocumentSyncTest::test_a_quiet_poll_never_loads_the_document_content` fails if that changes. When the caller is behind, the same response carries the document, its outline and its canvas stylesheet (`css`), because the style may be what changed. The request's optional integer `protocol` is accepted and not yet acted on; it exists so a later phase can tell tabs running old JavaScript to reload. `Editor::heartbeat()` and `Editor::leaving()` are EMPTY public methods kept only because a tab opened before the sync poll shipped still calls them (every 60 seconds, and on unload), and a missing method answers with an error page; remove them one release later.
