# Print

## PageSetup merge order and dompdf page_text mechanism
PageSetup::fromDocument(Document, DocumentStyle) merges $doc->page_setup (per-document override, set via DocumentSettings::savePageSetup()) OVER $style->tokens['page'] (DocumentStyleSeeder) via array_merge, so an explicit document value always wins; unknown size (not A4|A3|Letter) or orientation (not portrait|landscape) fall back to the class defaults (A4/portrait) rather than reaching the @page rule unvalidated, and margins go through App\Styles\TokenGuard::length() the same way CssBuilder does. Page numbers ({{ page }}/{{ pages }} in header/footer templates) cannot be resolved at HTML-build time - dompdf only knows a page number while it paginates the PDF - so PrintRenderer::html() leaves them for dompdf: any header/footer template containing them renders an EMPTY DOM band (PrintRenderer::band() returns html=''), and the real text (with {{ page }}/{{ pages }} rewritten to dompdf's own {PAGE_NUM}/{PAGE_COUNT} placeholders) is instead drawn onto every page's canvas by a <script type="text/php"> block calling Canvas::page_text($x,$y,$text,$font,$size) - dompdf's documented page-numbering convention (vendor/dompdf/dompdf/src/Adapter/CPDF.php::page_text(), which internally str_replaces {PAGE_NUM}/{PAGE_COUNT} in $text once per page via processPageScript). This requires Options::isPhpEnabled (set via Pdf::setOption(['isPhpEnabled'=>...]) on the Barryvdh\DomPDF\Facade\Pdf instance in PrintRenderer::pdf() - see "isPhpEnabled is enabled only when a text/php block is emitted" below for exactly when this is true vs false), or dompdf silently ignores the script tag (PhpEvaluator::evaluate() no-ops when !getIsPhpEnabled()). Because header/footer text is user-editable (DocumentSettings::savePageSetup(), validated only as nullable|string|max:200 - no content restriction), PrintRenderer::phpStringLiteral() escapes it as a safe single-quoted PHP literal (addcslashes for backslash and single-quote) and neutralises literal '</script' before it is embedded in the eval'd <script type="text/php"> block - otherwise a crafted footer template is a PHP eval() code-injection / extra-script-tag-injection vector at PDF-render time, not just an HTML-escaping concern.

## Page setup edits never re-save content
page_setup (size/orientation/margins/header/footer) is not document content - `App\Livewire\Documents\DocumentSettings::savePageSetup()` writes it directly via `$this->document->update(['page_setup' => [...]])` and must NEVER also call `App\Documents\DocumentStore::save()` afterwards. `DocumentStore::save()` unconditionally does `$doc->version = $doc->version + 1; $doc->save();` and fires the `on_save` webhook every time it runs - passing `['version' => 'none']` only skips `cutVersion()` (no `DocumentVersion` snapshot row), it does NOT stop the version-number bump or the webhook. Found in review round 1: an earlier version of `savePageSetup()` re-saved `$doc->content_json` unchanged "to re-render header/footer variables", but header/footer `{{ variable }}` templates are substituted at print/PDF time by `PrintRenderer::band()` (reading `$doc->variables` fresh on every render), never baked into `content`/`content_json` - so there was nothing to re-render, and the re-save only bumped `documents.version` and spammed `on_save` webhooks for a page-format-only change. Regression test: `tests/Feature/Documents/DocumentSettingsPageSetupTest.php` asserts `$doc->version` is unchanged and `document_versions` stays empty after `savePageSetup()`. Contrast with `App\Livewire\Documents\Editor::setStyle()` (Task 6), which legitimately DOES re-save through `DocumentStore::save()` because changing a document's style changes its numbering (Outline rules come from `$style->tokens['numbering']` - see `.ai/rules/styles.md`), i.e. actual content changes.

## isPhpEnabled is enabled only when a text/php block is emitted
`PrintRenderer::pdf()` does not unconditionally set `Options::isPhpEnabled`; it checks `str_contains($html, 'type="text/php"')` on the HTML `html()` just built and only passes `['isPhpEnabled' => true]` to `Pdf::setOption()` when a header/footer template actually needed `{{ page }}`/`{{ pages }}` (see the `page_text` mechanism above). Most documents have no page-number tokens in their header/footer, so most PDF renders now run with dompdf's `eval()`-backed PHP evaluator off entirely, narrowing that security surface to only the renders that need it.

## page_text() offsets are derived from PageSetup margins, in points
`document.blade.php`'s `<script type="text/php">` block no longer hardcodes `page_text(40, 24, ...)` / `page_text(40, height-30, ...)`. `PrintRenderer::html()` converts `$setup->margins['left']`/`['top']`/`['bottom']` to points via `PrintRenderer::toPoints()` (1mm = 2.8346pt, 1cm = 28.346pt, 1in = 72pt; already-pt values pass through) and passes `pageTextX` (the left margin in points, shared by header and footer), `headerPageTextY` (inside the top margin band) and `footerPageTextYFromBottom` (inside the bottom margin band, subtracted from `$pdf->get_height()`) into the view - so header/footer page-number text tracks whatever margins the document/style actually configures instead of a fixed pixel guess.

## Header/footer variable substitution coerces non-scalar values to ''
`HeaderFooterBands::segments()`'s `{{ key }}` substitution only casts a `$doc->variables` value to string when `is_scalar($value)` is true; a non-scalar value (array, object, null already defaults via `?? ''`) becomes `''` instead of PHP's `(string)` cast, which on an array throws an `E_WARNING` ("Array to string conversion") and yields the literal text "Array" in rendered output. `page_setup` templates and `variables` are both user-editable, so a stray array-valued variable must degrade silently, not warn or leak "Array" into a printed document.

## `{{ page }}`/`{{ pages }}` classification lives in `HeaderFooterBands`, not `PrintRenderer`
The `{{ key }}` split, the `page`/`pages` field whitelist, and the non-scalar coercion rule above all live in `App\Print\HeaderFooterBands::segments()` (A4 pagination phase) — `PrintRenderer::band()` is now a thin caller that reassembles `segments()`'s output into its own `{html, pageText}` shape for dompdf's `page_text()` mechanism (see the rule above this one). The SAME `segments()` output also feeds `Editor::outline()`'s `headerSegments`/`footerSegments`, which the live pagination editor renders via `resources/js/editor/pagination/bands.js` (text nodes only, never `innerHTML` — the client-side half of this same escaping contract). Any future change to how `{{ page }}`/`{{ pages }}` are recognised belongs in `HeaderFooterBands`, the one place that whitelist is allowed to exist — not in `PrintRenderer`, and not reimplemented in JS.
