# Search

## Search access predicate is DocumentPolicy::view(), narrowed to the current team
SEARCH (App\Search\DocumentSearch) is the ONE document search since R2-7 - the documents page and the header both call it - and it reads ONE company: `CompanyDocuments::scope()` (a document belongs to its team; a document with no team only to its owner, and only while they stand in no company). Nothing from another company is a search result, however it was shared: those documents are reached through "Shared with me" (owner decision 2026-11-27). `DocumentPolicy::view()` is then checked row by row on what is left, so the rule can only narrow, never widen past the policy. The query selects only the columns a result row and the policy need, with each document's team loaded alongside (the policy reads it). pgsql matches documents.search_vector (the generated tsvector over title + search_text) ranked by ts_rank; sqlite (production and tests) goes through App\Search\TextMatch, shared with the header search (CompanyDocuments): the title matches any part of a word (escaped LIKE), the body is looked up in the FTS5 table `documents_fts` (App\Search\FullTextIndex, R2-5): every word a quoted prefix, all required, ranked by bm25 with the title weighted 10x. The index is external-content over documents(title, search_text), kept in step by three triggers (documents_fts_ai/_ad/_au; the update trigger fires only on a change of title or search_text). A migration that rebuilds the `documents` table drops those triggers: the index is then unused (LIKE fallback) until `php artisan search:rebuild` - and FullTextSearchTest fails, so re-run FullTextIndex::install() at the end of any such migration. Both read search_text, which DocumentStore::fill() rewrites on every save - never search `content`, the rendered HTML, except through the narrow legacy clause (search_text IS NULL) that keeps documents not yet processed by `documents:migrate-to-json` findable. Queries shorter than two characters are not searches at all.
