# Deployment

## doc.infodot.co.za's real docroot is NOT DEPLOY_PATH/public - it's DEPLOY_PATH's PARENT directory
Confirmed live via `uapi DomainInfo single_domain_data domain=doc.infodot.co.za` on the server: the configured document root for the domain is `/home/infodotc/doc.infodot.co.za`, and `DEPLOY_PATH` (`/home/infodotc/doc.infodot.co.za/doc`) is a SUBDIRECTORY of it, not the same thing. This is a shared-hosting "flattened" Laravel layout from the original manual deploy: a hand-written `index.php` sits directly at the docroot and boots DEPLOY_PATH's vendor/bootstrap (`require __DIR__.'/doc/vendor/autoload.php'` etc.) - a DIFFERENT relative path than this repo's own `public/index.php` (`__DIR__.'/../vendor/autoload.php'`), which assumes `public/` sits directly inside the Laravel root. Every other static file under `public/` (`build/`, favicons, `robots.txt`, `sw.js`, `images/`) has its OWN separate copy sitting directly at the docroot.

`deploy.yml`'s "Transfer public assets to the real docroot" step rsyncs there (`$(dirname "$DEPLOY_PATH")`), never `index.php` (overwriting it with this repo's version would break every request instantly - wrong relative paths), with `build/` getting its own `--delete`-scoped sync to the docroot AND to `DEPLOY_PATH/public/build/` (the two copies described below: the browser fetches the first, `@vite` reads the second's manifest; old content-hashed files don't accumulate in either) and everything else getting a `--delete`-free sync (the docroot also holds `doc/` itself, an old `Dot.docs.tar.gz`, and `.well-known` for ACME/SSL - none exist under this repo's `public/`, so a `--delete` sync of the whole docroot would wipe all three).

**The incident this fixed:** for days (PRs #5-#10), every deploy correctly updated `DEPLOY_PATH/public/build/` - a path the webserver never serves - so Laravel kept reading its own current `manifest.json` and emitting correct asset hashes, while the browser's request for those exact URLs 404'd against the real, untouched-since-April docroot copy. Looked exactly like a stale LiteSpeed cache (and `public/.htaccess`'s `CacheLookup off` never even reached the real docroot's `.htaccess` for the same reason, so that "fix" was never live either); it was a wrong rsync destination the whole time. Lesson: on shared hosting, never assume `DEPLOY_PATH/public` IS the docroot - verify with `uapi DomainInfo single_domain_data domain=<domain>` before trusting any path-based deploy assumption.

**And the incident that fix caused (2026-10-16, after PR #17):** there are TWO copies of `build/`, and every deploy must write BOTH from the same build - the docroot's, which the browser fetches, and `DEPLOY_PATH/public/build/`, whose `manifest.json` is what `@vite` reads (`public_path()` is inside DEPLOY_PATH) to pick the hashed filenames it puts in the HTML. PR #12 MOVED the `build/` sync to the docroot rather than adding the docroot as a second destination, and `public/build` is gitignored so `git reset --hard` never refreshes it: the manifest Laravel reads was never written again. It looked fixed for weeks because no release between #12 and #17 changed any JS or CSS, so Vite produced identical content hashes and the stale manifest matched the docroot files by luck. #17 changed the bundle, the hashes moved, the docroot's `--delete` removed the files the stale manifest still named, and the site rendered unstyled with 404s while `/build/manifest.json` (the docroot copy) looked perfectly current. The transfer step now syncs `public/build/` to both places, and the deploy's last step, "Smoke-check the live site", fetches `/` and `/login` from the runner and fails the deploy unless every `build/` asset they reference answers 200: a deploy is green only once the live page has been seen loading its own assets.

## The app directory sits inside the web root - the root `.htaccess` is what keeps it private
Because the docroot is DEPLOY_PATH's parent, everything under DEPLOY_PATH is reachable as `https://doc.infodot.co.za/doc/...` unless something refuses it. Found live on 2026-10-01: `/doc/database/database.sqlite` (the entire production database) and `/doc/storage/logs/laravel.log` were downloadable by anyone, and had been since the SQLite move; only dotfiles (`.env`, `.git`) were refused, by the host. The repository's ROOT `.htaccess` (`Require all denied` plus a rewrite to 403) now denies every web request under DEPLOY_PATH - PHP's `require` reads the filesystem, so the app still boots. Never delete or loosen that file, never add an allow rule under it, and never put anything that must be publicly fetchable inside DEPLOY_PATH: public files go to the docroot through `deploy.yml`'s transfer step. `tests/Feature/AppDirectoryIsNotServedTest.php` only guards the file's presence and contents; the real check is a request - after any change to the layout, confirm `/doc/database/database.sqlite`, `/doc/storage/logs/laravel.log` and `/doc/composer.json` all answer 403. The same applies to anything dropped at the docroot by hand: an old `Dot.docs.tar.gz` of the source sat there, publicly downloadable, until it was moved out.

## The account's crontab is written only by deploy workflows, each touching only its own marker lines, with the write verified
This cPanel account's single crontab is shared by every Dot app. On 2026-08-31 a sibling app piped `crontab -l | grep -v ...; echo ...` into `crontab -`; the read failed under strict mode, the subshell printed nothing, and `crontab -` installed an EMPTY crontab: Dot.Mines' scheduler was dead for six weeks. This app's scheduler line (`# dot-doc`, needed because routes/console.php drains the mail queue from the scheduler and the systemd units in bootstrap.yml cannot be installed without sudo on this host) is written by `deploy.yml` with the verified block every Dot deploy shares: stop if the crontab cannot be read, touch only our marker lines, read back after writing and restore the previous crontab unless every other line survived. Never add a cron line by hand and never pipe into `crontab -`.

## Moving the document root to `<app>/public` (S-2e, prepared 2026-10-27, not done yet)
The deploy handles both layouts, so the hosting-panel change can happen between two deploys. In the code step, right after `git reset --hard`, it asks `uapi DomainInfo single_domain_data domain=doc.infodot.co.za` for the document root; when that is `<app>/public` it moves the tracked root `.htaccess` aside (`.htaccess.docroot-is-public-disabled`), because LiteSpeed also reads `.htaccess` files in the PARENT of the document root and `Require all denied` there refuses every request (this took the site to 403 on the first attempt). In the transfer step, when the document root is `<app>/public`, only `build/` is written, in place; nothing is synced to the parent. In the flattened layout both steps behave as before. `tests/Feature/DeployHandlesStandardLayoutTest.php` guards both branches.

Order for the move (owner): merge and deploy this change first (the site keeps the flattened layout), then change the Document Root of doc.infodot.co.za to `doc.infodot.co.za/doc/public` in cPanel's Domains page, read it back with `uapi`, run `~/bin/movecheck doc doc` on the host, and check `/`, `/login`, `/up` and a build asset. Rollback: set the Document Root back to `doc.infodot.co.za`, `mv ~/doc.infodot.co.za/doc/.htaccess.docroot-is-public-disabled ~/doc.infodot.co.za/doc/.htaccess`. After the move the old docroot copy of `index.php`, `build/` and `Dot.docs.tar.gz` is no longer served.
