# Editor

## Editor bundle mirrors DocumentSchema; block ids are 8-char base62
Every TipTap node name and attribute in resources/js/editor/ is one contract with App\Documents\Schema\DocumentSchema, not a second implementation: heading{level,numbered}, figure{kind}, caption, toc{depth,entries}, crossRef{targetId,kind,label}, pageBreak, sectionBreak{setup}, callout{tone}, columns{count}, column, variable{key}, image, taskList/taskItem and the table nodes. DocumentStore::save() runs DocumentSchema::validate() and rejects an unknown node type or a block without a valid id, so the editor cannot invent either.

Every node in DocumentSchema::BLOCKS carries attrs.id: 8 characters of base62 (/^[0-9A-Za-z]{8}$/), generated by extensions/blockId.js to mirror App\Documents\Schema\BlockId. BLOCK_TYPES in that file must stay in lockstep with DocumentSchema::BLOCKS - a type missing from the list saves without an id and the save throws "Block <type> has no valid id". Inline nodes (crossRef, variable) carry NO id.

Heading and figure numbers are never computed in JS. Editor::outline() (server, style-driven) is the only source: it is seeded into the page as data-outline on the wire:ignored editor host and refreshed through @this.outline() after each save, and outline.js fans it out to the heading-number decorations, the toc node view and every crossRef node view. Renderer-visible attribute names win over library defaults - see extensions/textAlign.js, which renames TextAligns textAlign attr to align because HtmlRenderer reads attrs.align.

## The floating toolbar has a keyboard contract, and every part of it is explicit
"Alt text" is the one command in the product whose entire purpose is accessibility, and `ui/bubble.js`'s toolbar is its only home — so nothing about reaching or operating it may rest on a browser default. Four rules, all of them measured by `tests/js/toolbar.test.js`:

1. **Activation is bound, never inherited.** `bindActivation()` binds `mousedown` (the default must be prevented before the editor loses the selection to the click, which a `click` listener is too late for) AND `keydown` for Enter/Space. It tells the callback WHICH it was: a registry command ends in `chain().focus()`, so a key press would apply one tool and drop the writer back in the paper — focus returns to the button unless the press deliberately moved it into the toolbar (the link and alt-text fields). The two form rows' submit buttons and their inputs get the same treatment through `submitOnKey`, with `preventDefault()` keeping it to ONE submission.
2. **`role="toolbar"` means a roving tabindex.** One tab stop for the whole toolbar; Left/Right move between the visible buttons and wrap, Home/End go to the ends (`rovingMove`). Every button being its own tab stop is not the ARIA pattern and makes a reachable toolbar worse than an unreachable one.
3. **Two routes in, both required.** Tab from the paper reaches it because the toolbar is appended to `<body>` and the top bar is the FIRST element of `.shell` (see .ai/rules/views.md — moving the bar back breaks this). `Alt+F10` / `F10` is the APG route for when something else follows the canvas (the dock, the comment sidebar) and it calls `place()` FIRST, because a selection that has not changed fires no `selectionUpdate` and nothing else would bring a dismissed toolbar back. Escape dismisses it and returns the caret.
4. **A blur into the toolbar is not leaving it.** `blurLeavesToolbar()` reads `relatedTarget` (the only reading available while the blur is in flight) and `toolbarHoldsFocus()` reads `activeElement` once it has settled. Hiding on either is what kept "Alt text" mouse-only even after it answered Enter.

## Every mark in DocumentSchema::MARKS must be registered, or the document opens EMPTY
TipTap's createNodeFromContent SWALLOWS a schema error and returns an empty doc, so one unregistered node or mark turns the whole document into a blank page - and the next keystroke autosaves that blank page over the real content. This is why extensions/textStyle.js exists even though nothing in the UI writes textStyle yet. Two guards, both in index.js mount(): the Editor is built with `enableContentCheck: true` + `onContentError`, and the incoming JSON is also checked against the live schema by the pure `isContentValid(json, {nodes, marks})` in validation.js. Either failing calls failClosed(): read-only, a visible `.dotdoc-content-error` banner, and autosave OFF. Never "fix" a schema mismatch by relaxing that - register the node/mark instead.

## Style-bearing attrs are whitelisted on BOTH sides, and normalised before they persist
paragraph/heading.align, columns.count, image.src and textStyle.color all end up inside a `style` (or `src`) attribute. A document that arrives from the sync poll goes straight to schema.nodeFromJSON() in remoteTransaction() (sync/apply.js) and NEVER passes through parseHTML, so parseHTML alone is not a guard. resources/js/editor/attrs.js holds the client whitelists (normaliseAlign / alignStyle, normaliseColumnCount 2-4, isValidImageSrc, normaliseColor hex-only, asText for anything handed to a DOM-spec renderer as a text node) and is dependency-free so tests/js can run it under `node --test` (`npm test`). The server mirrors it in HtmlRenderer::alignStyle()/renderColumns() and, so a bad value never persists at all, in DocumentSchema::normalise(), which DocumentStore::create()/save() run right after ensureIds(). Change one side and you must change the other. Block ids from stored JSON also go through dom.js blockSelector() (CSS.escape) before they become a querySelector.

## Other people's saves arrive through the sync engine, and applyRemote() is a minimal, non-destructive change
There is no websocket in production, so an open editor polls. `resources/js/editor/sync/engine.js` (no DOM, fetch or timers of its own; all injected, tested in `tests/js/sync.engine.test.js`) asks `POST /documents/{uuid}/sync` for the current version: every 1.5 s while somebody else has the document open, every 10 s alone, not at all while the tab is hidden. The page gives it a host (`engineHost()` in `sync/host.js`, see the next section) with four states - `clean`, `busy` (a save in flight), `dirty` (unsaved typing or an unresolved conflict) and `closed` (fail-closed) - and it hands a newer document to the editor ONLY in `clean`. In `dirty` it reports a conflict: saving is suspended and the writer chooses "Keep mine" (save over the newer version, with the base moved up to it; the server keeps the replaced version in the history) or "Load theirs" (park the local text as a `stale-` draft, apply the newer document, and hold the local text in the bridge's `setAside`). "Put it back" restores what `setAside` holds, and the save that follows goes as an overwrite exactly like Keep mine (`overwriteOwed`), because it too replaces a version on purpose: the one this tab loaded. Without the flag the replaced version was kept in the history only if `DocumentStore::shouldCut()` happened to cut one. One choice at a time: `keepMine()` and `loadTheirs()` do nothing while `syncState()` is `busy`, or Load theirs pressed while a Keep mine save is in the air leaves this tab showing one version and claiming the other as its base. Apart from `applySuggestion()` (a document this page itself just had stored), the engine is the only thing that applies a server document; an Echo `.document.updated` broadcast, when a socket exists, just calls `poke()`. The engine tracks `seen` (newest version downloaded), which is not the same as the bridge's `baseVersion` (what the editor's content is based on, sent with every save) - keeping them apart is what stops an unresolved conflict re-downloading the document on every poll; `refetch(version)` is how `sync/host.js` asks (from `enterConflict()` and `loadTheirs()`) for a document the engine has already seen and no longer holds. The engine stops for good on 401, 419, 403 or 404 ONLY when the response has a JSON body, which is the application answering; the same status with no JSON body is a firewall or rate limiter in front of it and is retried with back-off. A document the editor cannot open is reported once through `onRefused` and polling goes on. A host callback that THROWS must not end the loop either (the next poll would never be armed, and the tab would stop following and drop out of presence with nothing on screen to say so): a throw from `applyRemote` is treated as a refusal, and anything thrown during a poll is swallowed before the next poll is armed.

`syncState()` decides `dirty` from the bridge's own `unsaved` flag, not only from `handle.pending`: the bundle stops reporting pending the moment it HANDS a document to `persist()`, long before the server has stored it, so a save that never answers (offline, a 500 and a 419 all leave the `$wire` promise pending for ever) or is rejected would otherwise read as `clean` and the next remote document would replace text that exists nowhere else. `unsaved` is set on every local `update` (`edited()`) and cleared in three places only: when `clearDraftIfSettled()` confirms a save of exactly what the editor holds, when a server document has been applied (`applyFromSync()`, and `applySuggestion()` for an accepted suggestion), and when `syncState()` finds the editor back at exactly what the server last confirmed. That last one needs the bridge's `confirmed` (the document as a JSON string: as the page opened it, as the last accepted save stored it, or as the last server document left it): an edit undone again inside the bundle's 1.2 s debounce never reaches `persist()`, because the bundle finds nothing to send, so nothing else would ever clear the flag - the tab would stop following for good and raise a conflict over text it does not hold. `persist()` keeps ONE save in the air: Livewire sends a second call after the first with the arguments it was CALLED with, so a second autosave would state the old base and the tab would conflict with itself; a save asked for meanwhile is remembered in `resave` (also while a conflict stands, see the next section) and sent by `resendIfOwed()`, which runs when a save answers, on every answered poll and from `backOnline()` (what the `app-online` listener calls), and which also re-sends a save that has not answered in 15 seconds - it never saves a copy the writer has not touched. `adoptVersion()` (after this page's own style change) moves the base up only when the new version is exactly one past it; anything else means somebody else saved first, and adopting the version would make the next save erase their text. (`applySuggestion()` passes `contentLoaded` and moves the base regardless, because it has just put exactly that version into the editor.)

`handle.applyRemote(json, {force})` replaces only the range that differs (`sync/narrow.js` `diffRange()`, built on `Fragment.findDiffStart/findDiffEnd`), in one transaction tagged `addToHistory: false` (a collaborator's paragraph is not something YOU can undo) and `preventUpdate: true` (so TipTap does not emit `update` and arm the autosave, which would send the document straight back). The transaction itself is built by `remoteTransaction(state, json, ReplaceStep)` in `sync/apply.js`, which imports nothing from the editor bundle so that `tests/js/sync.apply.test.js` runs every branch of it; `applyRemote()` keeps the guards, the metas, the dispatch and the autosave bookkeeping, and nothing under `tests/js` can load it - change what an apply DOES in `apply.js`, with a test. A document that does not end in a paragraph gets the editor's own empty trailing paragraph: TipTap's TrailingNode appends it inside the apply's own dispatch (where `preventUpdate` keeps it out of the autosave), `remoteTransaction()` carries it over on every later apply instead of removing and re-adding it, and it is saved only with the writer's next edit. Do NOT tag the transaction `skipTrailingNode`: that only postpones the paragraph to the next transaction of any kind (the heading-number plugin dispatches one after every apply), where it arrives with a fresh id, fires `update` and arms the autosave, so every following tab saves its own trailing paragraph and the tabs conflict although nobody typed. The range is applied as a `ReplaceStep`, NOT `tr.replace()`: `tr.replace()` runs ProseMirror's fitter, which re-shapes an open slice around `isolating` nodes (table cells, figures, columns) and returns a DIFFERENT document without throwing. The result is checked against the target and falls back to a whole-document replace if it differs. The caret, the undo history and the page-break decorations survive for everything outside the one replaced range; when a single apply carries two separate changes, the text between them is replaced too, a caret there moves to the end of the range and local edits there can no longer be undone. It returns false without touching anything when the content is invalid, when the editor is fail-closed, or - unless `force` - when there is unsaved local typing. True means "applied", not "identical": a local repair plugin (a ragged table, a figure with no image) may still adjust what arrived and a trailing paragraph may follow it, and neither is saved from there. Compare documents as ProseMirror NODES, never as JSON: `DocumentSchema::normalise()` strips `align` when it is null and the editor emits `align: null` on every paragraph, so the two JSON forms of one document never match. Parsed nodes still differ in two places, and `remoteTransaction()` levels both before it diffs: `toc.entries` and `crossRef.label`, which `Outline::apply()` stamps into the stored document (levelled with attribute steps, or a re-stamped contents list stretches the range from the top of the document to the real change), and an empty `sectionBreak.setup` or `doc.vars`, which PHP serialises as `[]` where the editor holds `{}`.

## The editor page's save and conflict decisions live in sync/host.js, which holds no state
Every decision the editor page makes about a save (send it, hold it, send it again, refuse it, overwrite on purpose), about a newer document (follow it, raise the conflict, set text aside, put it back), about a version to adopt and about the offline draft is made in `resources/js/editor/sync/host.js`. The bundle exposes it as `window.DotDoc.sync.createSyncHost(view, env)`, beside `createTabId({crypto, random, now})` (this tab's id: `crypto.randomUUID()`, else 16 bytes of `crypto.getRandomValues()`, and `Math.random` only in a browser with no crypto at all). `tests/js/sync.host.test.js` runs the module under `node --test` together with the real `sync/engine.js`, against a fake server, editor handle, draft store and clock. The `x-data` component in `resources/views/livewire/documents/editor.blade.php` keeps only the reactive state fields, the page glue (mounting the editor, starting the engine, the window listeners, Echo, `destroy()` and the like) and one-line delegates such as `persist(json, options) { return this.syncHost().persist(json, options); }`. New decision logic goes into the module with a test that fails first - NOT into the `x-data` attribute, where neither PHPUnit nor `node --test` can run it (the three faults below were written there, and no test could see them). Like the rest of `sync/`, the module is dependency-free: no import, no DOM, no `window`, no Livewire, no clock and no console of its own. Everything outside the state object arrives in `env`, which the Blade method `syncHost()` builds: the editor handle and the engine (both parked on the element), `@this.saveContent()`, `@this.refreshPresence()`, the outline refresh, the status word, `window.offlineDraft`, `DotDoc.documentsDiffer`, where an arriving outline and stylesheet go, `window.confirm`, `Date.now`, and `console.info` / `console.error`.

The module holds NO state of its own. Alpine re-creates the component's data object whenever a render changes the `x-data` string, while the handlers bound at first load stay on the FIRST object (`.ai/rules/livewire.md`), so every call has to read and write the object it was made on. `syncHost()` therefore returns `createSyncHost(this, {...})` afresh for every call, and the module assigns to `view.<field>` directly; it never copies a field into a local to write it back later, which across an `await` would put back a stale value. The engine's callbacks come from `this.syncHost().engineHost()` inside `startSync()`, so they stay with the object that started the engine, as the page's own handlers do. Do not cache a host or give the module a variable of its own; the test "each call reads and writes the state object it was built from" pins that a call works on the object it was built from. The module reads and writes `saving`, `savingSince`, `unsaved`, `resave`, `confirmed`, `overwriteOwed`, `conflict`, `setAside`, `syncNotice`, `memberKey`, `baseVersion`, `aiError` and `tick`, and only reads `docUuid` and `documentVersion`; a new state field is declared in the `x-data` object, never in the module.

Three behaviours are rules, each pinned by tests that failed before the fix:
1. **A save asked for while another of this tab's saves is in the air is always remembered as owed (`resave`), also while a conflict stands.** In `persist()` the `saving > 0 && !force` check comes BEFORE the conflict check, because the save in the air may be the Keep mine save that ends the conflict, and text handed over meanwhile must not be turned away by a conflict that save is about to end. (`force` is Keep mine itself, which cannot start while a save is in the air.) For the same reason a stored save that did not settle (`clearDraftIfSettled()` false: the editor no longer holds exactly what was stored) leaves a save owed: that answer may arrive after the text typed since was handed to `persist()` and turned away by the very conflict the answer ends, and nothing else would send that text before the next keystroke. `resendIfOwed()` runs at the end of the same answer and sends only when the text is unsaved, no conflict stands and the bundle's debounce is not armed, so while the writer is still typing the debounce sends it, as before.
2. **The 15 second save expiry lives in ONE helper, and it marks the save as owed.** `saveInTheAir()` (`SAVE_EXPIRY_MS`) is the only place a save expires: it stops waiting (`saving = 0`) and sets `resave`. `syncState()` and `resendIfOwed()` both ask it, so whichever notices first leaves the same state behind. Do not write a second expiry check: the one `syncState()` carried forgot that the save was owed.
3. **An error after a stored save is not reported as a failed save.** `persist()` gives the save's promise two handlers on ONE `then(onAnswer, onFailed)`, never `then().catch()`: `onFailed` is for the request itself failing (it reports "Not saved"), and nothing that goes wrong after an answer reaches it. Inside `onAnswer` the answer is handled in a try/catch that sends a throw to `env.log`, and the outline refresh after it has its own catch, so a throw or a failed outline refresh after a stored save neither shows "Not saved" nor counts the save as answered a second time.

## The pagehide/destroy flush goes by BEACON, never Livewire
Livewire cannot issue a request during unload at all: its CommitBus defers every `$wire` call on a 5 ms timer that an unloading page never runs, so `$wire.saveContent()` does not even create a request. `flushSave({beacon: true})` (called by the `pagehide` listener and by `destroy()`) instead POSTs `{_token, content, base_version}` as an `application/json` Blob through `navigator.sendBeacon()` to `POST /documents/{uuid}/autosave` (`App\Http\Controllers\DocumentAutosaveController`, `['version' => 'none']`, no version snapshot). sendBeacon cannot set headers, so there is no `X-CSRF-TOKEN`; the token rides in the JSON body, which is fine because Laravel's CSRF middleware reads `$request->input('_token')` and `input()` reads the decoded JSON for an application/json request. The beacon's outcome is unknowable from the page, so the offline draft stays as the second safety net. The beacon states the version the page's copy was based on (`getBaseVersion` mount option); the server answers 409 and writes nothing when somebody has saved since.

## Draft recency is decided by VERSION, never by a clock; drafts are cleared only when the save settled
`Editor::saveContent()` returns `['ok' => bool, 'conflict' => bool, 'version' => int]` ($wire actions resolve with the return value). `offline.js` `saveDraft(uuid, json, baseVersion)` stores the version the last successful save reported, seeded from `$document->version` at mount; `loadDraft()` returns `{json, savedAt, baseVersion}`. On mount a draft is offered ONLY when `draft.baseVersion === document.version` (nobody has saved since) AND `DotDoc.documentsDiffer(draft, editor.getJSON())` is true - that comparison strips `toc.entries` and `crossRef.label`, the two fields `Outline::apply()` stamps into stored JSON, or every single load would look like a difference. A LOWER baseVersion is not restorable and not this page's to destroy either: it is parked under a `stale-<uuid>` key with a `console.info` explaining why, and offered back through Put it back when it differs from the document (see the parked-draft section below). Do NOT go back to comparing `savedAt` with `updated_at` - those come off two different clocks, and a client running slow discards real offline work.

Clearing a draft is equally strict. After a save resolves with `ok`, the draft is dropped only when `handle.pending` is false AND the editor's current JSON still equals the snapshot string captured when THAT request was sent - saves resolve out of order, and an older one must never delete the only copy of newer keystrokes. A rejected save (`ok: false`) keeps the draft and renders the `content` error in the status area. In fail-closed mode (`handle.autosaves === false`) the bridge does nothing at all: no draft write, no draft read, no clear, no save - what the editor is holding then is not the document. `applyFromSync()` also clears the draft, once a newer server document has been applied: the engine applies only to a tab whose `unsaved` flag is false, and the one forced apply, Load theirs, parks the editor's text under `stale-<uuid>` before it (a browser that cannot keep drafts has none to clear), so nothing unsaved is ever lost by that clear. A draft the writer restores at page load is NOT cleared by the restore itself - the save that follows can be refused as a conflict - but by `persist()` once that save has settled.

## Raw HTML enters through applyHtml(), never setContent()
With `enableContentCheck: true`, `editor.commands.setContent(html)` THROWS on a tag this schema does not register, and the throw comes out of an Alpine handler with nothing to catch it. Every raw-HTML path (the AI panels' replace and insert) goes through `handle.applyHtml(html, {mode})`: `generateJSON(html, extensions)`, then `isContentValid()` against the live schema, then `isEmptyDocument()` - `doc` is `block+`, so HTML this schema drops entirely comes back as ONE EMPTY PARAGRAPH, and `content.length === 0` would not catch it, but replacing a real document with it would erase the document. Only then does it apply, with `errorOnInvalidContent: false`, inside try/catch. False leaves the document untouched and shows the error in the status area. An accepted AI suggestion arrives as server-stored JSON and goes through `applyRemote()` for the same reason.

## Every block insert goes through the registry's blockInsert() guard
`resources/js/editor/guards.js` holds `isInCaption()` and `blockInsert()` (dependency-free, exercised by `npm test`). A `caption` is inline-only, so a block inserted there splits the figure from its media. EVERY path that inserts a block passes the guard: the registry entries the palette and slash menu list, the extensions' own keyboard shortcuts (`pageBreak`'s `Mod-Enter`), the image picker and `uploadImage()` in index.js (which re-checks at INSERT time, because the file dialog is asynchronous), and the Blade toolbar buttons - which call `window.DotDoc.run(ed(), 'table')` rather than `ed().chain()...insertTable()`. A toolbar button that reaches for `editor.chain()` directly is a button that can split a figure.

## An asynchronous insert re-runs the caption guard at INSERT time, not at request time
isInCaption() answers for the selection at the moment it is called, which is worthless for anything with an await in it. uploadImage() in index.js goes through a file dialog AND an HTTP request, and the writer can click into a figure caption while either is open - inserting against the selection at that later moment splits the figure (torn caption, phantom image{src:null} figure, orphan image). The rule: capture editor.state.selection.from BEFORE the await, map it forward with an editor.on(transaction) handler for as long as the request is in flight (removed in a finally), and insert with insertContentAt(blockInsertPosition(editor, pos), node) - never setImage()/insertContent(), which both go to the selection. blockInsertPosition() (guards.js, dependency-free, covered by npm test) returns the mapped position, or the position AFTER the enclosing figure when it has drifted inside one, or null when the position will not resolve. A figure is built as one node ({figure, [image, caption]}) rather than image-then-wrapInFigure, because wrapInFigure works off the selection too; focusInsertedCaption() then finds the caption in a bounded scan forward from the insert position.

## A draft that cannot be restored is PARKED, and parked drafts expire after 7 days
Never delete a draft the writer might still want. Three paths park instead of deleting: a draft whose baseVersion is behind the document (somebody saved since), the editor's own text when the writer chooses Load theirs in the conflict notice (loadTheirs() also holds it in the bridge's setAside, which Put it back restores), and a draft the writer DECLINED at the restore confirm() - that confirm has no undo behind it, so a mis-click must not destroy the only copy of somebody offline work. All three call window.offlineDraft.parkStaleDraft(uuid, json, baseVersion), which writes the row under stale-<uuid> with a parkedAt stamp and replaces whatever was parked for that document before, and then clearDraft() on the live key (Load theirs clears it through applyFromSync(), so only once the newer document is in the editor). Parked rows are not kept for ever: offline.js purgeStaleDrafts() runs once per app boot from initOfflineSupport() and deletes stale- rows older than STALE_TTL_MS (7 days), dating a row by parkedAt, falling back to savedAt for rows parked by an older build, and sweeping a parked row that carries neither. The decision itself is the pure staleDraftIsExpired(row, now, ttl), covered by npm test; it NEVER expires a live draft row, however old, because age says nothing about whether it is still the only copy of something. A draft parked at page load because the document has moved on is also held in the bridge's setAside, so the status strip offers Put it back - but only when DotDoc.documentsDiffer(draft, editor.getJSON()) is true. The unload beacon leaves a draft behind every time it succeeds (the page is gone before it could clear it), and that draft says exactly what the document already says: offering it would show Your text was set aside after every tab closed in mid-sentence.

## `resizable: true`'s live table bypasses `Table.configure({ HTMLAttributes })` entirely
`@tiptap/extension-table`'s `Table` node has a normal `renderHTML({ HTMLAttributes })` that merges `this.options.HTMLAttributes` in - the usual way a TipTap node picks up a configured class. But `Table.addProseMirrorPlugins()` only calls that when the table has NO custom NodeView; whenever `resizable: true` AND `editor.isEditable` (true for the live canvas), it registers `prosemirror-tables`' `columnResizing({ View: this.options.View })` instead, and `View` (default `TableView`, exported from `@tiptap/extension-table`) builds its `<table>` with a bare `document.createElement('table')` that never reads `this.options.HTMLAttributes` at all. `Table.configure({ HTMLAttributes: { class: 'doc-table' } })` alone is therefore a no-op on the live editable canvas - confirmed live, the class stayed `""` regardless - even though it correctly reaches the SAME node in any non-editable/non-resizable render path.

Found while wiring up `doc-table`, the class `App\Styles\CssBuilder::tableRules()` scopes its border/zebra/header-shading CSS to (app/Styles/CssBuilder.php): `App\Documents\Render\HtmlRenderer::renderTable()` already emitted it correctly server-side (print/export/share), but nothing in the JS bundle ever put it on a live table, so DocumentStyle's table tokens were invisible while editing. Fixed with `resources/js/editor/extensions/table.js`'s `DocTableView`, a `TableView` subclass that calls `super()` then adds the class to `this.table`, passed as `Table.configure({ resizable: true, View: DocTableView, HTMLAttributes: {...} })` - the `HTMLAttributes` stays too, as a defensive no-cost fallback for any future non-resizable/non-editable path. The general lesson: a TipTap node with a custom `View` (any node, not just tables) needs its class/attributes applied INSIDE that view, never assumed to flow through `HTMLAttributes` just because the node also defines a normal `renderHTML()`.

## A pagination view mode that "replaces the canvas" must mount inside `.canvas`, not beside it
`resources/css/paper.css`'s `.canvas` (the flex wrapper `.paper` sits inside) is `min-height:100%` unconditionally - that rule has nothing to do with `.paper`'s own visibility, so `.canvas` stays a full-viewport-tall EMPTY box the instant `.editor-main.dotdoc-mode-X .paper{display:none}` hides its only real content. Task 8's live browser verification (not catchable by any unit test, since it needs real layout geometry) found `viewModes.js`'s `applyMode()` mounting the Print Preview iframe AND the Multi-Page grid as siblings of `.canvas` (both appended directly to `canvasEl`/`.editor-main`) - which landed both of them below that still-full-height empty `.canvas`, off-screen below the fold on any document taller than one viewport. Both existed since Task 7; neither was ever visible in a real browser before this. The fix (now in place) is `canvasEl.querySelector('.canvas') || canvasEl` as the mount target for anything meant to REPLACE `.paper` - any FUTURE mode that hides `.paper` and shows something else must mount that something-else the same way, and also give it `width:100%` (`.canvas` is `display:flex`, so an unsized child collapses to its own min-content instead of the canvas's available width - `.dotdoc-multi-page-grid{width:100%}` is the existing example).

## A cloned `.paper` needs its OWN background/ink rule - it cannot rely on inheriting one
`viewModes.js`'s thumbnail/multi-page previews clone content into a wrapper (`.dotdoc-thumbnail-inner`) that ALSO carries the `paper` class, so Document Style rules apply to the cloned content - but a clone mounted in the thumbnails RAIL sits outside `.canvas` entirely, so `.canvas .paper`'s (`paper.css`) `background:var(--paper);color:var(--paper-ink)` base rule never reaches it, and neither does `CssBuilder`'s own `.paper{background:#fff}` fallback once something more specific is present. Confirmed via live browser inspection in dark mode (Task 8): a `.paper`-classed clone with no explicit background of its own inherits the dark chrome behind it.

**Fixed:** `.dotdoc-thumbnail .dotdoc-thumbnail-inner.paper{background:var(--paper);color:var(--paper-ink)}` in `CssBuilder::paginationRule()`. Deliberately scoped to the thumbnail's own internal structure (`.dotdoc-thumbnail > .dotdoc-thumbnail-inner.paper`, the same DOM shape `renderThumbnail()` produces everywhere it's called) rather than to `.editor-main` - that is what makes ONE rule reach both the grid's thumbnails and the rail's identically, without needing two separate fixes for two different ancestor contexts. The general lesson: a clone that borrows a Document Style class for STYLING purposes needs its own background/ink declaration wherever its ancestor chain could plausibly make that class's background rule resolve to something other than an actual page, rather than assuming the rule that colours the REAL canvas will reach a clone the same way.

## The live canvas `.paper` must keep its OWN background at all times - never make it transparent to show a gap through it
An earlier version of `paginationRule()` made `.paper` itself `background:transparent;box-shadow:none` while paginated, on the theory that the true page-gap decoration (`.dotdoc-page-gap`) needed `.paper` to have no background for `--ground` (the desk behind the paper) to show through where two "pages" meet - then repainted `.paper>*` (every direct child) `#fff` to put the white back on each real content block. That distorted every page, not just the gaps: `.paper`'s own padding (the page's margins) and the space BETWEEN two ordinary children (a paragraph's own `margin-bottom`) are not covered by any `.paper>*` child either, so the WHOLE document rendered as a scatter of disconnected white text blocks on bare canvas - margins included - instead of one continuous A4 sheet. Confirmed live: every screenshot taken of the editor while that rule was in place showed exactly that, reported directly as "it should show as a full A4 page, instead of just text with white backgrounds."

**Fixed** by removing both rules and leaving `.paper` alone: it keeps its ordinary background (`.canvas .paper{background:var(--paper)}`, paper.css) and box-shadow at all times, paginated or not. The `.dotdoc-page-gap`/`.dotdoc-page-shadow` widgets are already OPAQUE, normal-flow children inserted exactly at the computed break point - they interrupt the paper's own continuous background where a break genuinely falls, without needing the whole element to go transparent to make that happen. Confirmed live afterward, including a forced multi-page split: each page renders as one seamless white sheet, and the gap between two pages still shows clearly as a solid `--ground`-coloured band cutting across it. The general lesson: to punch a visual hole at ONE specific point in an otherwise-continuous element, give the thing AT that point an opaque background - don't make the continuous element transparent and try to repaint everything else around the hole.

## Focus mode reaches the shell chrome via `:has()`, and never touches panel state
`.editor-main.dotdoc-mode-focus` cannot hide `.topbar`/`.rail`/`.dock` with an ordinary descendant selector - per .ai/rules/views.md, all three are `.editor-main`'s own ancestor's SIBLINGS inside `.shell` (layouts/app.blade.php's grid: topbar/rail/canvas/dock), several levels above where `CssBuilder::paginationRule()`'s CSS is even injected (editor.blade.php's `<style id="doc-style">`, itself nested inside `#canvas`). The fix is `.shell:has(.editor-main.dotdoc-mode-focus) .topbar,...,.dock{display:none}` - `:has()` is the only pure-CSS way to react, from an ancestor, to a class on a descendant of a DIFFERENT branch of that ancestor's subtree. It deliberately never writes `data-panel-state`/`data-panel-user` (the rail/dock panel-state machine, .ai/rules/views.md's "Collapsed by default" section) - it only ever hides, never opens or closes, so a panel the writer had open before Focus mode stays recorded as open underneath the whole time and simply reappears, unrestored, the moment the mode class is removed. Confirmed live: `data-panel-state` read `"expanded"` before, during (while `display:none`), and after a Focus-mode round trip, for both an expanded and a collapsed starting state.

`.topbar`'s grid ROW is not `auto` sized (`.shell{grid-template-rows: var(--topbar-h) auto minmax(0, 1fr)}`, a fixed 52px first row) the way `.rail`/`.dock`'s COLUMNS are (shell.css's own comment: "A collapsed panel is display:none, which empties its column, which collapses the track to zero") - so `.topbar{display:none}` alone leaves a dead 52px band of bare `--ground` at the top instead of Focus mode's promised "single continuous scroll of prose". The same `:has()` condition also sets `.shell{grid-template-rows:0 auto minmax(0,1fr)}` to collapse that row; confirmed live via `getComputedStyle(shell).gridTemplateRows` before/after.

## A mid-table page-boundary widget is `position:absolute`, never a normal-flow child of `<tbody>`
An UNRESIZED TipTap table (`Table.configure({resizable: true})` with no manual column drag, so no `colwidth` attrs on any cell - the common case) has no explicit width; its rendered column widths come from ordinary CSS auto-layout, driven by whatever content the browser considers part of each row. A NORMAL-FLOW page-boundary widget landing MID-TABLE (`decorations.js`'s `renderBoundaryWidget()`, `.dotdoc-page-boundary` - footer/gap/header bands, `contain:layout`) used to be inserted as a direct, in-flow child of that table's own `<tbody>`, sitting between two `<tr>` siblings - and, being wide (its bands span close to the full page), measurably distorted the table's OWN auto-layout column computation: removing it shrank the table's columns back down, and repeated reflows (each `getBoundingClientRect()` call, each unrelated `view.dispatch()` a table's NodeView re-validates against) could read a DIFFERENT column width each time, drifting with no guaranteed fixed point - confirmed live while first building `resources/js/editor/pagination/decorations.js`'s table-header-repeat feature (design spec §2.2): a version that re-measured and wrote back a "corrected" width on every pass made the reading grow on EVERY edit anywhere in the document, unboundedly, because each write was itself a DOM mutation feeding the next reading.

**Fixed** by removing the widget from the table's layout algorithm entirely, per CSS 2.1 §17.2.1: an out-of-flow (`position:absolute`) child of a table-row-group never gets wrapped in the anonymous row/cell that would otherwise fold it into column-width computation - confirmed live, restoring the table's TRUE, undistorted columns the instant this applies, stable (not merely bounded) across repeated unrelated edits. `.dotdoc-page-boundary.dotdoc-page-boundary-in-table{position:absolute;left:{margin};right:{margin}}` (`CssBuilder::paginationRule()`) is positioned inside `.paper` itself (`resources/css/paper.css`'s `.canvas .paper{position:relative}` - `.paper` beats `.canvas-region`'s own `container-type: inline-size`, .ai/rules/views.md, as the nearest positioned ancestor); `top` is computed PURELY from already-measured geometry (`decorations.js`'s `tableSplitOverlayTopPx()`: the table's own live top, plus `headerHeight` and the summed `rowHeights` up to the split - never by reading another element's current, possibly-not-yet-updated flow position).

Three further pieces this fix needed, all non-obvious:

1. **`left/right:0` is NOT the same as "matches every other boundary's width."** A normal (non-table) boundary is an ordinary in-flow CHILD of `.paper`, so it inherits `.paper`'s own page-margin `padding` (`CssBuilder::paperRule()`) for free, confining it to the content column. But CSS 2.1 §10.3.7 resolves an ABSOLUTELY positioned descendant's `left`/`right` against its containing block's PADDING BOX, which - for `.paper` as the positioned ancestor - spans `.paper`'s full width, margins included. `left:0;right:0` therefore bled the mid-table widget's header/footer band across the ENTIRE page, edge to edge, instead of stopping at the ~560px content column every normal boundary's band respects - confirmed live (its band measured full paper width; a normal boundary's band on the same page measured the content column). Fixed by setting `left`/`right` to the exact same page-margin values `.dotdoc-page-band`'s own padding already uses (`CssBuilder::horizontalMargins()`), so a mid-table split's running header/footer lines up with every other page's, pixel for pixel.

2. **Reserving the vertical space the widget no longer occupies.** Removing it from flow means nothing pushes the table's next row down by the widget's own height any more - `decorations.js`'s `buildTableSplitGapDecorations()` reserves it instead, via a REAL `Decoration.node()` (`padding-bottom`, carried as a `--dotdoc-split-gap` custom property) on every cell of the row immediately before the split. Confirmed live that a RAW DOM write (`element.style.paddingBottom = ...`, or even just `element.classList.add(...)`) on that row gets REVERTED by ProseMirror's own view-tree reconciliation within about one repagination cycle - it treats a document node's DOM as something it owns and silently corrects it back to what the node's schema/decorations say it should be. A `Decoration.node()` is the opposite: it IS part of what ProseMirror itself considers that cell's expected render, so it survives the exact reconciliation that discards a raw write. `measureBlocks()`'s own row-height reading has to subtract this same amount back out via `rowSplitGapPx()` (reading the same custom property), or a later pass would treat the synthetic gap as real row content and feed a wrong height into `computeBreaks()`.

3. **A `Decoration.widget()` at a fixed KEY does not track a moving target.** Once the widget's position is an explicit, JS-computed `top` (rather than something the browser keeps in sync for free via normal flow), THAT computed value has to be part of the decoration's key, or ProseMirror will happily reuse a stale cached widget - with its stale `top` - whenever the key doesn't happen to differ, discarding whatever fresh `top` this pass just computed. Confirmed live: editing content BEFORE the table (shifting the table's own position on the page) left the widget rendered ~28px off from where the split actually fell, because neither the header text nor blockIndex/offset/pageCount happened to change from that edit. `repaginate()` folds the computed `overlayTopPx` directly into the key to close this.

Also: `measureOverlayHeight()` (which measures the widget's natural height before deciding how much space to reserve) must insert its probe element as a descendant of `.paper` itself, never `document.body` - `.dotdoc-page-band`'s font-size/colour read CSS custom properties (`--doc-size-small`, `--doc-muted`, ...) declared ON `.paper` by `CssBuilder::paperRule()`, a document-style token, not a `:root` global; measuring outside `.paper` entirely left them undefined, silently producing a WRONG height that didn't match the same content rendered for real moments later.
