# Editor

## Editor bundle mirrors DocumentSchema; block ids are 8-char base62
Every TipTap node name and attribute in resources/js/editor/ is one contract with App\Documents\Schema\DocumentSchema, not a second implementation: heading{level,numbered}, figure{kind}, caption, toc{depth,entries}, crossRef{targetId,kind,label}, pageBreak, sectionBreak{setup}, callout{tone}, columns{count}, column, variable{key}, image, taskList/taskItem and the table nodes. DocumentStore::save() runs DocumentSchema::validate() and rejects an unknown node type or a block without a valid id, so the editor cannot invent either.

Every node in DocumentSchema::BLOCKS carries attrs.id: 8 characters of base62 (/^[0-9A-Za-z]{8}$/), generated by extensions/blockId.js to mirror App\Documents\Schema\BlockId. BLOCK_TYPES in that file must stay in lockstep with DocumentSchema::BLOCKS - a type missing from the list saves without an id and the save throws "Block <type> has no valid id". Inline nodes (crossRef, variable) carry NO id.

Heading and figure numbers are never computed in JS. Editor::outline() (server, style-driven) is the only source: it is seeded into the page as data-outline on the wire:ignored editor host and refreshed through @this.outline() after each save, and outline.js fans it out to the heading-number decorations, the toc node view and every crossRef node view. Renderer-visible attribute names win over library defaults - see extensions/textAlign.js, which renames TextAligns textAlign attr to align because HtmlRenderer reads attrs.align.

## Block ids are kept unique by the repair plugin, and the block a transaction did not touch keeps the id
The editor never holds two blocks with one id. `BlockIdRepair` (extensions/blockId.js, registered in `buildExtensions()` beside `BlockId`) runs after every transaction that changed the document, and a block that shares its id with another block gets a fresh `base62(8)` id in an appended transaction. Nested blocks count (a list item's paragraph, a table cell); a block with no id yet is left for UniqueID.

Why it is needed: TipTap's UniqueID only compares ids among the blocks INSIDE the range a transaction changed. While `applyRemote()` still kept the undo history across somebody else's change, an undo could take back the id UniqueID gave the second half of a split while the split itself was dropped (its position was inside the range the remote change replaced). The emptied half then carried the id the first half still had, UniqueID did not notice, `DocumentSchema` refused every save from that tab ("Duplicate block id"), Keep mine included, and the tab could never save again. Seen in a real browser with two accounts; `tests/js/uniqueIds.test.js` replays it as transactions with prosemirror-history, first without the plugin (the defect) and then with it. `applyRemote()` now empties the undo history after a remote change (see "A remote change empties the undo and redo history" below), which closes that route; the repair stays, because nothing else keeps ids unique whatever a transaction does.

Which block keeps the id matters, because comments and cross-references point at block ids and the server's copy says which block owns one: **the block the transaction did NOT touch keeps it**, and the touched one gets the new id. A block is touched when it STARTS inside a changed range: a block that was inserted, the new half of a split, a block whose attributes were set. A block that was only typed in, or that merely contains or follows the change, is not. When every block sharing the id was touched, or none was, the first in document order keeps it. The server's `DocumentSchema::ensureIds()` (`.ai/rules/app.md`) is the same rule for a document that arrives without having been through this plugin: it only sees a finished document, so it keeps the FIRST in document order and gives every later holder a fresh id (the "none was touched" fallback, applied always).

The decision and the transaction are in `resources/js/editor/uniqueIds.js` (`duplicateIds()`, `changedRanges()`, `uniqueIdsTransaction()`), which imports nothing so `node --test` runs it; the plugin only calls it. Change what the repair does THERE, with a test. What must stay true:
- The repair is tagged `addToHistory: false` and never `preventUpdate`. The document changed, so `update` must fire and the autosave must run. (TipTap decides `update` from the ROOT transaction, so a repair inside a remote apply stays out of the autosave, and `applyRemote()` reads `editor.getJSON()` after the dispatch, repair included.)
- It runs on every keystroke: nothing unless a transaction in the batch changed the document, then ONE pass over the block nodes, and the changed ranges are worked out only when two blocks do share an id.
- It ends: a document with unique ids appends nothing, a new id is never one the document already uses, and a generator that cannot supply an unused id leaves the block alone.
- The id is set with an attribute step (`setNodeAttribute`). Such a step has an empty step map, so `changedRanges()` takes its range from `step.pos`, and UniqueID, which reads step maps, does not react to it.
- It stays BEHIND UniqueID. UniqueID declares priority 10000 and the repair has the default, so UniqueID is asked about a transaction first and Enter and paste never reach the repair with a duplicate. Asked first, the repair would decide a split by document order, where UniqueID deliberately leaves the id with the half that holds the text.
- prosemirror-history records a transaction appended to an undo or a redo on the opposite stack whatever its `addToHistory` says, so the repair's step can be taken back by the next redo or undo. The plugin runs after that transaction too; the test's redo and second undo pin it.

## The floating toolbar has a keyboard contract, and every part of it is explicit
"Alt text" is the one command in the product whose entire purpose is accessibility, and `ui/bubble.js`'s toolbar is its only home — so nothing about reaching or operating it may rest on a browser default. Four rules, all of them measured by `tests/js/toolbar.test.js`:

1. **Activation is bound, never inherited.** `bindActivation()` binds `mousedown` (the default must be prevented before the editor loses the selection to the click, which a `click` listener is too late for) AND `keydown` for Enter/Space. It tells the callback WHICH it was: a registry command ends in `chain().focus()`, so a key press would apply one tool and drop the writer back in the paper — focus returns to the button unless the press deliberately moved it into the toolbar (the link and alt-text fields). The two form rows' submit buttons and their inputs get the same treatment through `submitOnKey`, with `preventDefault()` keeping it to ONE submission.
2. **`role="toolbar"` means a roving tabindex.** One tab stop for the whole toolbar; Left/Right move between the visible buttons and wrap, Home/End go to the ends (`rovingMove`). Every button being its own tab stop is not the ARIA pattern and makes a reachable toolbar worse than an unreachable one.
3. **Two routes in, both required.** Tab from the paper reaches it because the toolbar is appended to `<body>` and the top bar is the FIRST element of `.shell` (see .ai/rules/views.md — moving the bar back breaks this). `Alt+F10` / `F10` is the APG route for when something else follows the canvas (the dock, the comment sidebar) and it calls `place()` FIRST, because a selection that has not changed fires no `selectionUpdate` and nothing else would bring a dismissed toolbar back. Escape dismisses it and returns the caret.
4. **A blur into the toolbar is not leaving it.** `blurLeavesToolbar()` reads `relatedTarget` (the only reading available while the blur is in flight) and `toolbarHoldsFocus()` reads `activeElement` once it has settled. Hiding on either is what kept "Alt text" mouse-only even after it answered Enter.

## Every mark in DocumentSchema::MARKS must be registered, or the document opens EMPTY
TipTap's createNodeFromContent SWALLOWS a schema error and returns an empty doc, so one unregistered node or mark turns the whole document into a blank page - and the next keystroke autosaves that blank page over the real content. This is why extensions/textStyle.js exists even though nothing in the UI writes textStyle yet. Two guards, both in index.js mount(): the Editor is built with `enableContentCheck: true` + `onContentError`, and the incoming JSON is also checked against the live schema by the pure `isContentValid(json, {nodes, marks})` in validation.js. Either failing calls failClosed(): read-only, a visible `.dotdoc-content-error` banner, and autosave OFF. Never "fix" a schema mismatch by relaxing that - register the node/mark instead.

## Style-bearing attrs are whitelisted on BOTH sides, and normalised before they persist
paragraph/heading.align, columns.count, image.src and textStyle.color all end up inside a `style` (or `src`) attribute. A document that arrives from the sync poll goes straight to schema.nodeFromJSON() in remoteTransaction() (sync/apply.js) and NEVER passes through parseHTML, so parseHTML alone is not a guard. resources/js/editor/attrs.js holds the client whitelists (normaliseAlign / alignStyle, normaliseColumnCount 2-4, isValidImageSrc, normaliseColor hex-only, asText for anything handed to a DOM-spec renderer as a text node) and is dependency-free so tests/js can run it under `node --test` (`npm test`). The server mirrors it in HtmlRenderer::alignStyle()/renderColumns() and, so a bad value never persists at all, in DocumentSchema::normalise(), which DocumentStore::create()/save() run right after ensureIds(). Change one side and you must change the other. Block ids from stored JSON also go through dom.js blockSelector() (CSS.escape) before they become a querySelector.

## Other people's saves arrive through the sync engine, and applyRemote() is a minimal, non-destructive change
There is no websocket in production, so an open editor polls. `resources/js/editor/sync/engine.js` (no DOM and no fetch: the request function is handed in, and so are the visibility check and the timer, which fall back to always-visible and the global `setTimeout` when they are not; tested in `tests/js/sync.engine.test.js`) asks `POST /documents/{uuid}/sync` for the current version: every 1.5 s while somebody else has the document open, every 10 s alone, not at all while the tab is hidden. The page gives it a host (`engineHost()` in `sync/host.js`, see the next section) with four states - `clean`, `busy` (a save in flight), `dirty` (unsaved typing or an unresolved conflict) and `closed` (fail-closed) - and it hands a newer document to the editor ONLY in `clean`. After every poll that completed, answered or not (a firewall's 403, a 5xx, no network; only the poll that stops the engine for good is left out), it gives the host a tick (`onPolled`), and that tick is where a save that is owed gets sent: saving must not depend on the poll being answered. In `dirty` it hands the document to `mergeOrConflict()` (see "A newer document over unsaved typing is MERGED block by block" below): the typing is merged into it block by block and saved on the new base, and only when the merge cannot be done does it report a conflict: saving is then suspended and the writer chooses "Keep mine" (save over the newer version, with the base moved up to it; the server keeps the replaced version in the history) or "Load theirs" (park the local text as a `stale-` draft, apply the newer document, and hold the local text in the bridge's `setAside`, with `setAsideFrom = 'conflict'` and `setAsideBase` = the version just loaded). "Put it back" restores what `setAside` holds. Keep mine and Put it back both replace a version on purpose, and BOTH set `overwriteOwed` (so does a merge whose deletion beats a block somebody else edited and saved, ORed in and never assigned: see the Phase 2 section at the end): Keep mine at the moment it moves the base up, Put it back before the text goes in. While it is set, every save from the tab says it overwrites (the Keep mine save, a retry, an ordinary autosave, the unload beacon), and the server makes sure the replaced version is in the history first. It is cleared only by an accepted save that itself carried the flag (`persist()` captures that when the save is sent), by a server document being applied, by a merge or an accepted suggestion that leaves nothing of the typing to save (no save is left to carry it), or by the editor being back at the confirmed document (a Put it back that cannot put the text in leaves the flag as it found it; `overwriteFloor` and the draft stamp are described in the Phase 2 section). When the overwrite was remembered only by the one save Keep mine sent, a failed save or a tab closed inside the debounce lost it: the next save was accepted on the moved base, and the replaced version was in the history only if `DocumentStore::shouldCut()` happened to have cut one. Put it back ASKS first (`PUT_BACK_QUESTION`, through `env.confirm`) unless the writer can be taken to know what it replaces: it does not ask only when the text came from Load theirs (`setAsideFrom === 'conflict'`), the document has not moved since (`baseVersion === setAsideBase`) and nothing on the page is unsaved. A no changes nothing and the offer stays. "Discard" (`discardSetAside()`) withdraws the offer and touches nothing else: nothing is sent, the page is as it was, the parked copy stays. When the text came from Load theirs it asks first (`DISCARD_QUESTION`, through `env.confirm`): that text is the writer's own unsaved typing and is in no saved version, so after Discard only the parked copy holds it; a draft from an earlier visit (`setAsideFrom === 'draft'`) is withdrawn without a question, because the page took nothing away. `setAside`, `setAsideFrom` and `setAsideBase` are cleared together (`forgetSetAside()`), and only by a Put it back that went in and by Discard. One choice at a time: `keepMine()` and `loadTheirs()` do nothing while `syncState()` is `busy`, or Load theirs pressed while a Keep mine save is in the air leaves this tab showing one version and claiming the other as its base. Apart from `applySuggestion()` (a document this page itself just had stored), the engine is the only thing that applies a server document; an Echo `.document.updated` broadcast, when a socket exists, just calls `poke()`. The engine tracks `seen` (newest version downloaded), which is not the same as the bridge's `baseVersion` (what the editor's content is based on, sent with every save) - keeping them apart is what stops an unresolved conflict re-downloading the document on every poll; `refetch(version)` is how `sync/host.js` asks (from `enterConflict()` and `loadTheirs()`) for a document the engine has already seen and no longer holds. The engine stops for good on 401, 419, 403 or 404 ONLY when the response has a JSON body, which is the application answering; the same status with no JSON body is a firewall or rate limiter in front of it and is retried with back-off. A document the editor cannot open is reported once through `onRefused` and polling goes on. A host callback that THROWS must not end the loop either (the next poll would never be armed, and the tab would stop following and drop out of presence with nothing on screen to say so): a throw from `applyRemote` is treated as a refusal, and anything thrown during a poll is swallowed before the next poll is armed. Every answer of `POST /documents/{uuid}/sync` also carries `can_edit`, a boolean from the same `update` gate `Editor::canEdit()` asks (not cached): the engine hands it to the host (`onAccess` -> `accessFromPoll()` in `sync/host.js`), where `false` is a confirmed downgrade (the read only page of `lockReadOnly()`, words parked; when a refused save's question is still out, it answers it) and `true` never re-enables a read only page (a reload does that; it only lifts the hold a refused save left while its question is out). The field is additive, so `PROTOCOL` did not move: an old client ignores it, and an old server sends none (no field, no change).

`syncState()` decides `dirty` from the bridge's own `unsaved` flag, not only from `handle.pending`: the bundle stops reporting pending the moment it HANDS a document to `persist()`, long before the server has stored it, so a save that never answers (offline, a 500 and a 419 all leave the `$wire` promise pending for ever) or is rejected would otherwise read as `clean` and the next remote document would replace text that exists nowhere else. `unsaved` is set on every local `update` (`edited()`) and cleared in three ways only: when `clearDraftIfSettled()` confirms a save of exactly what the editor holds, when a server document has been applied or merged into the typing (`applyFromSync()`, `applySuggestion()` for an accepted suggestion, and `mergeOrConflict()`, the draft merge and the suggestion merge, which leave it set exactly when something of the typing is still to be saved), and when `settleIfBackAtConfirmed()` finds the editor back at exactly what the server last confirmed. That last one needs the bridge's `confirmed`: the document as a JSON string, as the page opened it, as the last accepted save stored it, or as the last server document left it. It is the document of the version `baseVersion` names, and it is `null` whenever that is not known: from the moment one of this tab's saves is given up on or its request fails outright (the server may have stored it; only the answer is lost), and from the moment Keep mine moves the base up to a version the editor never held, until a save is accepted or a server document applied. Nothing is settled while it is null. The check exists because an edit undone again inside the bundle's 1.2 s debounce never reaches `persist()` (the bundle finds nothing to send), so nothing else would ever clear the flag: the tab would stop following for good, raise a conflict over text it does not hold, and save a document its writer did not change the next time the browser came back online. `settleIfBackAtConfirmed()` is called from `syncState()`, from `resendIfOwed()` and from `putBack()`, always AFTER `saveInTheAir()` has answered no: while a save is in the air the server may be about to hold something other than `confirmed`, and settling there dropped the owed save of an undo and said Saved over a document the server did not hold. The engine asks `syncState()` only when it holds a newer document (Keep mine and Load theirs ask it too); what runs the check on every completed poll is the call in `resendIfOwed()`. The four paths that no save answers for (`settleIfBackAtConfirmed()`, `applyFromSync()`, `applySuggestion()`, and `mergeOrConflict()` when a merge leaves nothing of the typing to save) also report `('good', 'Saved')` to the shell's save word, which otherwise stays on Editing although nothing is unsaved, and they report only when they actually take the tab from unsaved to nothing unsaved: a reader who follows a document has nothing to say. Load theirs says it through `applyFromSync()` and not again itself. A save's own answer reports Saved only when `clearDraftIfSettled()` is true, that is, when the stored document is what the editor holds; otherwise the save stays owed and the word stays on Editing. `persist()` keeps ONE save in the air: Livewire sends a second call after the first with the arguments it was CALLED with, so a second autosave would state the old base and the tab would conflict with itself; a save asked for meanwhile is remembered in `resave` (also while a conflict stands, see the next section) and sent by `resendIfOwed()`, which runs when a save answers, after every poll that completed (answered or not: the engine's `onMembers` and `onPolled` callbacks) and from `backOnline()` (what the `app-online` listener calls). A save that has not answered in 15 seconds is given up on and owed again, and `persist()` notices that itself, so a tab whose polls are blocked still sends its next autosave. `resendIfOwed()` sends only text that is unsaved here. It never sends a copy the writer has not touched, and that includes one the writer changed and changed back, because it runs the settle check before it sends anything. (When the fate of an earlier save is not known, `confirmed` is null, nothing is settled, and an undo is sent rather than written off.) `adoptVersion()` (after this page's own style change) moves the base up only when the new version is exactly one past it; anything else means somebody else saved first, and adopting the version would make the next save erase their text. (`applySuggestion()` passes `contentLoaded` and moves the base regardless, because it has just put exactly that version into the editor.)

`handle.applyRemote(json, {force})` changes what differs BLOCK BY BLOCK (`blockSteps()` in `sync/apply.js`: a changed textblock inside the block only, any other changed block whole, deletions and insertions as their own steps, a deletion and an insertion at one point as one replace so the document never passes through an empty `doc`; the steps are probed on a copy first, a narrowed step that fails is retried whole, and when a step still fails, the probe does not reproduce the target, or there are more than `MAX_BLOCK_STEPS` (500) steps, it falls back to the one range that differs, `sync/narrow.js` `diffRange()` built on `Fragment.findDiffStart/findDiffEnd`, and then to the whole document), in one transaction tagged `addToHistory: false` (a collaborator's paragraph is not something YOU can undo) and `preventUpdate: true` (so TipTap does not emit `update` and arm the autosave, which would send the document straight back). The transaction itself is built by `remoteTransaction(state, json, ReplaceStep)` in `sync/apply.js`, which imports nothing from the editor bundle so that `tests/js/sync.apply.test.js` runs every branch of it; `applyRemote()` keeps the guards, the metas, the two dispatches (the change, then the transaction that empties the undo history) and the autosave bookkeeping, and nothing under `tests/js` can load it - change what an apply DOES in `apply.js`, with a test. A document that does not end in a paragraph gets the editor's own empty trailing paragraph: TipTap's TrailingNode appends it inside the apply's own dispatch (where `preventUpdate` keeps it out of the autosave), `remoteTransaction()` carries it over on every later apply instead of removing and re-adding it, and it is saved only with the writer's next edit. Do NOT tag the transaction `skipTrailingNode`: that only postpones the paragraph to the next transaction of any kind (the heading-number plugin dispatches one after every apply), where it arrives with a fresh id, fires `update` and arms the autosave, so every following tab saves its own trailing paragraph and the tabs conflict although nobody typed. The range is applied as a `ReplaceStep`, NOT `tr.replace()`: `tr.replace()` runs ProseMirror's fitter, which re-shapes an open slice around `isolating` nodes (table cells, figures, columns) and returns a DIFFERENT document without throwing. The result is checked against the target and falls back to a whole-document replace if it differs. A caret or a page-break decoration in a block no step touches stays where it is (the steps are per block); a caret inside a block that changed is mapped by ProseMirror and lands at the end of the change. Only in the one-range fallback (a move, more than `MAX_BLOCK_STEPS` steps, a step that cannot be probed) is everything between the first and the last difference replaced, and a caret there moves to the end of the range. The undo history does NOT survive: see the next section. It returns false without touching anything when the content is invalid, when the editor is fail-closed, or - unless `force` - when there is unsaved local typing. True means "applied", not "identical": a local repair plugin (a ragged table, a figure with no image) may still adjust what arrived and a trailing paragraph may follow it, and neither is saved from there. Compare documents as ProseMirror NODES, never as JSON: `DocumentSchema::normalise()` strips `align` when it is null and the editor emits `align: null` on every paragraph, so the two JSON forms of one document never match. Parsed nodes still differ in two places, and `remoteTransaction()` levels both before it diffs: `toc.entries` and `crossRef.label`, which `Outline::apply()` stamps into the stored document (levelled with attribute steps, or a re-stamped contents list stretches the range from the top of the document to the real change), and an empty `sectionBreak.setup` or `doc.vars`, which PHP serialises as `[]` where the editor holds `{}`.

## A remote change empties the undo and redo history
After a remote transaction that changed the document, `applyRemote()` dispatches a second transaction, `clearHistoryTransaction(state)` (`sync/apply.js`, beside `remoteTransaction()`; `tests/js/sync.history.test.js`), and the editor has nothing to undo and nothing to redo. Undo then reaches back only as far as the last change that came from somebody else; edits made afterwards are undoable as usual. It holds for every caller of `applyRemote()`: a followed change, Load theirs and an accepted AI suggestion. (Put it back and the draft restore use `setContent`, not `applyRemote()`.)

The reason: prosemirror-history keeps its stacks valid across a transaction that is not an undo step by mapping every stored step through that transaction's step map. That is exact when the other person's change arrives as the small steps they actually made, and it is NOT safe for the one coarse replacement `remoteTransaction()` builds: a stored step whose range touches the replaced range is mapped onto the content that arrived. Press Enter at the start of "Hello", let somebody else type "Above" into the new paragraph and "Well, " in front of "Hello", then undo: the inverse of the split now covers exactly what they typed and deletes it, and the next autosave stores that. The same mapping produced the duplicate block id of the section above. `tests/js/sync.history.test.js` replays the case with the history kept (the lost text is asserted, in a bare state and in TipTap's own editor, so the test fails if prosemirror-history ever changes this) and then with the clearing transaction.

**Never make the remote transaction undoable, and never keep the stacks across it** - not even "when no stored step touches the replaced range": a mistake in such a check is silent data loss again. Collaborative undo needs remote changes to arrive as exact steps, which is the step log of Phase 3. It costs little until then. A remote document is not only ever applied to a tab with no unsaved typing: the ENGINE applies one only to such a tab, and the applies that go over unsaved typing, with `force`, are a MERGED document (the typing is in it, and what could not be kept is offered back: `mergeOrConflict()`, the draft merge and the suggestion merge in `sync/host.js`) and the writer's own choice: Load theirs, which sets the typing aside first, and an accepted suggestion that could not be merged, which sets it aside first too. What must stay true:
- It is a transaction of its OWN, dispatched directly after the remote one, never a meta on the remote transaction. prosemirror-history records a transaction appended to one that carries its meta on the opposite stack whatever its `addToHistory` says, and plugins do append to the remote dispatch (TrailingNode, UniqueID, the id repair).
- It has no steps and is tagged `addToHistory: false` and `preventUpdate`, so it changes neither the document nor the selection and TipTap emits no `update` for it (`Editor.dispatchTransaction()` returns before the emit when the root transaction carries `preventUpdate` or no transaction changed the document): the autosave is not armed, the tab is not marked as edited, and `applyRemote()`'s bookkeeping after it (`saveTimer`, `dirty`, `lastSaved`) holds.
- A remote document the editor already shows (`tr.docChanged` false) dispatches nothing and leaves the history alone.
- prosemirror-history has no public call that clears it. The builder finds the plugin among `state.plugins` by its key string (`history$`) and hands it an empty state (the plugin's own `spec.state.init()`) under that key as `{historyState}`, which is how the package's own undo and redo commands replace the state. Those are internals: after an upgrade of prosemirror-history or TipTap, the tests in `tests/js/sync.history.test.js` are what says whether they still hold.
- A state with no history plugin gets `null` and nothing is dispatched. A throw while building or dispatching it is logged with `console.error` and `applyRemote()` still returns true, because the document IS applied; it is never swallowed silently, because an editor that kept its history across a remote change is the unsafe state.

## The editor page's save and conflict decisions live in sync/host.js, which holds no state
Every decision the editor page makes about a save (send it, hold it, send it again, refuse it, overwrite on purpose), about a newer document (follow it, raise the conflict, set text aside, put it back), about a version to adopt and about the offline draft is made in `resources/js/editor/sync/host.js`. The bundle exposes it as `window.DotDoc.sync.createSyncHost(view, env)`, beside `createTabId({crypto, random, now})` (this tab's id: `crypto.randomUUID()`, else 16 bytes of `crypto.getRandomValues()`, and `Math.random` only in a browser with no crypto at all). The module also exports `unloadSaveBody()` (the unload beacon's body, see the beacon section), the constants `SAVE_EXPIRY_MS`, `MERGE_ATTEMPTS`, `MERGE_FETCH_EXPIRY_MS` and `LOST_ROWS`, and the sentences `PUT_BACK_QUESTION`, `PUT_BACK_UNSAVED_WARNING`, `DISCARD_QUESTION`, `LOAD_THEIRS_REPLACES_QUESTION`, `DISMISS_LOST_QUESTION`, `DISMISS_LOST_UNKEPT_QUESTION`, `DISMISS_LOST_FAILED_NOTICE`, `DISMISS_LOST_CHANGED_NOTICE`, `PUT_BACK_FAILED_NOTICE` and `DRAFT_MERGE_QUESTION`; the bundle and the tests import those, and they are not on `window.DotDoc.sync`. `tests/js/sync.host.test.js` runs the module under `node --test` together with the real `sync/engine.js`, against a fake server, editor handle, draft store and clock. The `x-data` component in `resources/views/livewire/documents/editor.blade.php` keeps only the reactive state fields, the page glue (mounting the editor, starting the engine, the window listeners, Echo, `destroy()` and the like) and one-line delegates such as `persist(json, options) { return this.syncHost().persist(json, options); }`. New decision logic goes into the module with a test that fails first - NOT into the `x-data` attribute, where neither PHPUnit nor `node --test` can run it (the three faults below were written there, and no test could see them). Like the rest of `sync/` it takes nothing from outside `sync/` (its one import is `./merge.js`, the lost-row helpers; `apply.js` imports `./narrow.js`; `insert.js` imports `./narrow.js`), and it has no DOM, no `window`, no Livewire, no clock and no console of its own. Everything outside the state object arrives in `env`, which the Blade method `syncHost()` builds: the editor handle and the engine (both parked on the element), `@this.saveContent()`, `@this.refreshPresence()`, the outline refresh, the status word, `window.offlineDraft`, `DotDoc.documentsDiffer`, where an arriving outline and stylesheet go, `window.confirm`, `Date.now`, and `console.info` / `console.error`.

The module holds NO state of its own. Alpine re-creates the component's data object whenever a render changes the `x-data` string, while the handlers bound at first load stay on the FIRST object (`.ai/rules/livewire.md`), so every call has to read and write the object it was made on. `syncHost()` therefore returns `createSyncHost(this, {...})` afresh for every call, and the module assigns to `view.<field>` directly; it never copies a field into a local to write it back later, which across an `await` would put back a stale value. The engine's callbacks come from `this.syncHost().engineHost()` inside `startSync()`, so they stay with the object that started the engine, as the page's own handlers do. Do not cache a host or give the module a variable of its own; the test "each call reads and writes the state object it was built from" pins that a call works on the object it was built from. The module reads and writes `saving`, `savingSince`, `saveSeq`, `expiredSaveSeq`, `unsaved`, `resave`, `confirmed`, `overwriteOwed`, `overwriteFloor`, `conflict`, `setAside`, `setAsideFrom`, `setAsideBase`, `syncNotice`, `memberKey`, `baseVersion`, `aiError`, `tick`, `merging`, `mergeAttempts`, `known`, `sentSnapshot`, `unanswered`, `lost`, `putBackSeq`, `editable` (read; written only by a confirmed read only), `unsentKept` and `accessCheckSince`, and only reads `docUuid` and `documentVersion`; a new state field is declared in the `x-data` object, never in the module.

Three behaviours are rules, each pinned by tests that failed before the fix:
1. **A save asked for while another of this tab's saves is in the air is always remembered as owed (`resave`), also while a conflict stands.** In `persist()` the `saveInTheAir() && !force` check comes BEFORE the conflict check, because the save in the air may be the Keep mine save that ends the conflict, and text handed over meanwhile must not be turned away by a conflict that save is about to end. (`force` is Keep mine itself, which cannot start while a save is in the air.) For the same reason a stored save that did not settle (`clearDraftIfSettled()` false: the editor no longer holds exactly what was stored) leaves a save owed: that answer may arrive after the text typed since was handed to `persist()` and turned away by the very conflict the answer ends, and nothing else would send that text before the next keystroke. `resendIfOwed()` runs at the end of the same answer and sends only when the text is unsaved, no conflict stands and the bundle's debounce is not armed. While the debounce is armed the save STAYS owed (`resave` is left set): the debounce normally sends it, but when the editor is back at the document the bundle last handed over (a typo and a backspace) the debounce finds nothing to send, and that document may be one `persist()` only marked as owed. The next tick then sends it. Clearing `resave` at that point dropped the save for good while the word said Saved. `persist()` clears `resave` at the moment it sends, because the owed save is the one going out: left set, the flag outlived the send, and a save the server then rejected was sent a second time off it.
2. **The 15 second save expiry lives in ONE helper, and it marks the save as owed.** `saveInTheAir()` (`SAVE_EXPIRY_MS`) is the only place a save expires: it stops waiting (`saving = 0`), sets `resave`, and sets `confirmed` to null, because the save may have been stored and only its answer is known to be lost. It also remembers the number of the save it gave up on (`expiredSaveSeq`; every save `persist()` sends is numbered in `saveSeq`). The answer to a save given up on is used only while the tab has learnt nothing newer since that save left (nothing confirmed, the base where it was, and the server document the tab knows (`known`, version and json) the one it held at send time: a base number alone is fooled by Keep mine followed by Load theirs, which brings the base back to the number it had while the page shows another document); otherwise `persist()` logs it and ignores it, because adopting it would move the base onto a version the editor does not show (Load theirs after a Keep mine save that was given up on) and the next save would replace that version without the overwrite flag. A late answer never counts against `saving`, which by then counts the save that replaced it, and a late failure is only logged. Everything that decides on a save in the air asks it (`persist()`, `syncState()`, `resendIfOwed()`, `edited()`, `putBack()`), so whichever notices first leaves the same state behind; the one place that reads `saving` directly is the guard inside `settleIfBackAtConfirmed()`, whose three callers reach it only after asking. `persist()` asking it is what lets a tab whose polls are blocked keep saving: when it read `saving` directly, one lost answer turned every later autosave into an owed one until a poll was answered. Do not write a second expiry check: the one `syncState()` carried forgot that the save was owed.
3. **An error after a stored save is not reported as a failed save.** `persist()` gives the save's promise two handlers on ONE `then(onAnswer, onFailed)`, never `then().catch()`: `onFailed` is for the request itself failing (it reports "Not saved" and sets `resave`, so the next poll tick sends the text again), and nothing that goes wrong after an answer reaches it. Inside `onAnswer` the answer is handled in a try/catch that sends a throw to `env.log`, and the outline refresh after it has its own catch, so a throw or a failed outline refresh after a stored save neither shows "Not saved" nor counts the save as answered a second time.

## The pagehide/destroy flush goes by BEACON, never Livewire
Livewire cannot issue a request during unload at all: its CommitBus defers every `$wire` call on a 5 ms timer that an unloading page never runs, so `$wire.saveContent()` does not even create a request. `flushSave({beacon: true})` (called by the `pagehide` listener and by `destroy()`) instead POSTs `{_token, content, base_version, overwrite}` as an `application/json` Blob through `navigator.sendBeacon()` to `POST /documents/{uuid}/autosave` (`App\Http\Controllers\DocumentAutosaveController`, `['version' => 'none']`, no version snapshot). sendBeacon cannot set headers, so there is no `X-CSRF-TOKEN`; the token rides in the JSON body, which is fine because Laravel's CSRF middleware reads `$request->input('_token')` and `input()` reads the decoded JSON for an application/json request. The beacon's outcome is unknowable from the page, so the offline draft stays as the second safety net. The beacon also carries text the bundle already handed to Livewire when the host says it is unsent and unanswered (`unsentAtUnload()` in `sync/host.js`, passed as the `getUnsent` mount option: the text is unsaved and the last request failed, `saveFailures > 0`, or the back-off holds it, `saveRetryAt` in the future, or the save was given up on after 15 s and nothing is confirmed since, `unanswered`, or a save is still in the air, `saving`, whatever its age; never on a read only or fail-closed page. A save in its first 15 s is beaconed too: Livewire never rejects the promise of a call whose fetch failed, so the page cannot tell a dead request from a slow one before the expiry (`saveFailures` stays 0 in a real browser), and the closing page aborts the request. Both state the same base and overwrite flag, so the server stores the text once and refuses the other as stale, with no second history version): the bundle counts a document it has handed over as sent, so without that a tab closed at Not saved sent nothing. `beaconWanted()` decides (dirty and changed, or unsent, and never the same content twice: pagehide then `destroy()`), with the same base version and overwrite flag as any beacon; a stale base is answered 409 and writes nothing. The body is built by `unloadSaveBody()` in `sync/host.js` (there, so `node --test` can run it), from two mount options read at the moment of leaving: `getBaseVersion`, the version the page's copy was based on (the server answers 409 and writes nothing when somebody has saved since), and `getOverwrite`, whether the tab owes an overwrite (`overwriteOwed`), always sent as a real boolean because the server validates it as one. With `overwrite: true` the server first makes sure the version being replaced is in the history, exactly as it does for the Livewire save; without it, a tab closed inside the debounce after Put it back, or after a Keep mine save that failed, replaced the other person's text and kept it nowhere.

## Draft recency is decided by VERSION, never by a clock; drafts are cleared only when the save settled
`Editor::saveContent()` returns `['ok' => bool, 'conflict' => bool, 'version' => int|null]` ($wire actions resolve with the return value; `version` is null in one answer only, the refusal of a save that stated no base, because JavaScript from before saves stated one adopts any number it is handed as its draft's base: see `.ai/rules/app.md`). `offline.js` `saveDraft(uuid, json, baseVersion)` stores the version the last successful save reported, seeded from `$document->version` at mount, with one exception: while an overwrite is owed, `edited()` and the merges that rewrite the draft stamp it BELOW the base (`draftStamp()`): `Math.min(baseVersion, overwriteFloor ?? baseVersion) - 1`, where `overwriteFloor` is the base the owed overwrite FIRST became owed on. That text is not a draft of the version the base names, it is there to replace it; stamped with the base, a page opened after a crash would offer a plain restore and save it with no overwrite flag, and stamped below it every later page sets it aside, where Put it back saves it as an overwrite. One below the base alone is not enough: Keep mine moves the base up without writing a base row, so when an overwrite was already owed before it (a c2 merge, Put it back), one below the moved-up base can be exactly the version of the base row that earlier step wrote, and a reopened page would merge the draft as if nothing were owed and keep the other writer's words nowhere. Below the floor the draft is older than every base row written while the overwrite was owed. `loadDraft()` returns `{json, savedAt, baseVersion}`. On mount a draft is offered ONLY when `draft.baseVersion === document.version` (nobody has saved since) AND `DotDoc.documentsDiffer(draft, editor.getJSON())` is true - that comparison strips `toc.entries` and `crossRef.label`, the two fields `Outline::apply()` stamps into stored JSON, or every single load would look like a difference. A LOWER baseVersion is not restorable as it stands (Phase 2 first tries to MERGE it: see the last section) and not this page's to destroy either: it is parked under a `stale-<uuid>` key with a `console.info` explaining why, and when it differs from the document it is offered in the notice bar as a draft from an earlier visit, with Put it back (which asks first) and Discard (see the parked-draft section below). Do NOT go back to comparing `savedAt` with `updated_at` - those come off two different clocks, and a client running slow discards real offline work.

Clearing a draft is equally strict. After a save resolves with `ok`, the draft is dropped only when `handle.pending` is false AND the editor's current JSON still equals the snapshot string captured when THAT request was sent - saves resolve out of order, and an older one must never delete the only copy of newer keystrokes. A save that is not accepted keeps the draft: a rejected one (`ok: false, conflict: false`) renders the `content` error in the status strip, a stale one (`conflict: true`) starts a merge (`beginMerge()`) and raises the conflict notice only when that merge cannot be done: an impossible merge, `MERGE_ATTEMPTS` refusals in a row, or a document that did not arrive within 15 s. In fail-closed mode (`handle.autosaves === false`) the bridge does nothing at all: no draft write, no draft read, no clear, no save - what the editor is holding then is not the document. `applyFromSync()` also clears the draft, once a newer server document has been applied: the engine applies only to a tab whose `unsaved` flag is false; of the forced applies, Load theirs parks the editor's text under `stale-<uuid>` before it (a browser that cannot keep drafts has none to clear), and an accepted suggestion either merges the tab's text into what this page itself just had stored (`mergeSuggestion()`) or, when it cannot, sets the text aside before the suggestion goes in, so nothing unsaved of THIS tab's is lost by that clear without an offer. (The draft is keyed by document, not by tab: a second tab of the same browser that follows a save clears the first tab's draft too, until the first tab's next keystroke rewrites it. Known, not fixed.) Two more places clear a draft, both because a draft that says exactly what the server last confirmed protects nothing and would outlive the page - once anybody has saved, the next visit would find it differs from the document and offer to put back a copy that holds none of this writer's text: `edited()` clears it instead of writing it when the editor is back at `confirmed` and no save is in the air (while one is, the draft is kept: the server may be about to hold the very text that was just undone), and `settleIfBackAtConfirmed()` clears it when it settles the tab. A draft the writer restores at page load is NOT cleared by the restore itself - the save that follows can be refused as a conflict - but by `persist()` once that save has settled.

## Raw HTML enters through applyHtml(), never setContent()
With `enableContentCheck: true`, `editor.commands.setContent(html)` THROWS on a tag this schema does not register, and the throw comes out of an Alpine handler with nothing to catch it. Every raw-HTML path (the AI panels' replace and insert) goes through `handle.applyHtml(html, {mode})`: `generateJSON(html, extensions)`, then `isContentValid()` against the live schema, then `isEmptyDocument()` - `doc` is `block+`, so HTML this schema drops entirely comes back as ONE EMPTY PARAGRAPH, and `content.length === 0` would not catch it, but replacing a real document with it would erase the document. Only then does it apply, with `errorOnInvalidContent: false`, inside try/catch. False leaves the document untouched and shows the error in the status area. An accepted AI suggestion arrives as server-stored JSON and goes through `applyRemote()` for the same reason.

## Every block insert goes through the registry's blockInsert() guard
`resources/js/editor/guards.js` holds `isInCaption()` and `blockInsert()` (dependency-free, exercised by `npm test`). A `caption` is inline-only, so a block inserted there splits the figure from its media. EVERY path that inserts a block passes the guard: the registry entries the palette and slash menu list, the extensions' own keyboard shortcuts (`pageBreak`'s `Mod-Enter`), the image picker and `uploadImage()` in index.js (which re-checks at INSERT time, because the file dialog is asynchronous), and the Blade toolbar buttons - which call `window.DotDoc.run(ed(), 'table')` rather than `ed().chain()...insertTable()`. A toolbar button that reaches for `editor.chain()` directly is a button that can split a figure.

## An asynchronous insert re-runs the caption guard at INSERT time, not at request time
isInCaption() answers for the selection at the moment it is called, which is worthless for anything with an await in it. uploadImage() in index.js goes through a file dialog AND an HTTP request, and the writer can click into a figure caption while either is open - inserting against the selection at that later moment splits the figure (torn caption, phantom image{src:null} figure, orphan image). The rule: capture editor.state.selection.from BEFORE the await, map it forward with an editor.on(transaction) handler for as long as the request is in flight (removed in a finally), and insert with insertContentAt(blockInsertPosition(editor, pos), node) - never setImage()/insertContent(), which both go to the selection. blockInsertPosition() (guards.js, dependency-free, covered by npm test) returns the mapped position, or the position AFTER the enclosing figure when it has drifted inside one, or null when the position will not resolve. A figure is built as one node ({figure, [image, caption]}) rather than image-then-wrapInFigure, because wrapInFigure works off the selection too; focusInsertedCaption() then finds the caption in a bounded scan forward from the insert position.

## A draft that cannot be restored is PARKED, and parked drafts expire after 7 days
Never delete a draft the writer might still want. Three paths park instead of deleting (two more since Phase 2, named below): a draft whose baseVersion is behind the document (somebody saved since), the editor's own text when the writer chooses Load theirs in the conflict notice (loadTheirs() also holds it in the bridge's setAside, which Put it back restores), and a draft the writer DECLINED at the restore confirm() - that confirm has no undo behind it, so a mis-click must not destroy the only copy of somebody offline work. The copy of a draft just before the draft merge applies it, and the typing `setAsideTyping()` sets aside when an accepted suggestion cannot be merged, park the same way. Every one calls window.offlineDraft.parkStaleDraft(uuid, json, baseVersion), which writes the row under stale-<uuid> with a parkedAt stamp and KEEPS whatever was parked for that document before: in one transaction the earlier park moves to `stale-<uuid>@<ms>` (`<ms>` is its own parkedAt, `keepKeyFor()` appends -2, -3 on a clash) and the new one takes the plain key, which therefore always holds the latest park. Kept parks are swept by their own stamp, 7 days after THEIR park; the page offers them one after another when they were made to be offered (the queue paragraph in the Phase 2 section). Then clearDraft() on the live key (Load theirs clears it through applyFromSync(), so only once the newer document is in the editor). Parked rows are not kept for ever: offline.js purgeStaleDrafts() runs once per app boot from initOfflineSupport() and deletes stale-, lost- and base- rows (`parkedRowIsExpired()`; the kept `stale-<uuid>@<ms>` rows are stale- rows) older than STALE_TTL_MS (7 days), dating a row by parkedAt, falling back to savedAt for rows parked by an older build, and sweeping a parked row that carries neither. The decision itself is the pure staleDraftIsExpired(row, now, ttl), covered by npm test; it NEVER expires a live draft row, however old, because age says nothing about whether it is still the only copy of something. A draft parked at page load because the document has moved on is also held in the bridge's setAside, with setAsideFrom = 'draft' and setAsideBase = the version the page shows, so the notice bar under the editor's bar offers Put it back and Discard (notices with actions never go in the one-line status strip: see .ai/rules/livewire.md) - but only when DotDoc.documentsDiffer(draft, editor.getJSON()) is true. The unload beacon leaves a draft behind every time it succeeds (the page is gone before it could clear it), and until somebody else saves that draft says exactly what the document already says: offering it would put a notice up after every tab closed in mid-sentence. Once somebody HAS saved, the draft differs from the document and is offered, and the page cannot tell whether its text was never stored or was stored and then built on. So the source is recorded, the notice for a draft does not say Your text was set aside (the page took nothing away; it says a draft from the last visit differs from the document and may already be part of it), and putBack() asks before it replaces anything unless the text came from Load theirs a moment ago, the document has not moved since and nothing on the page is unsaved. Telling the two cases apart for certain needs the server to remember which saves it accepted (a save id written beside the draft); that is not built. Discard (discardSetAside()) removes only the offer: the parked copy stays for its 7 days, but nothing in the page offers it again, so getting it back means reading the stale- row by hand - which is why Discard asks first when the text is this tab's own, set aside by Load theirs, and not for a draft from an earlier visit.

## `resizable: true`'s live table bypasses `Table.configure({ HTMLAttributes })` entirely
`@tiptap/extension-table`'s `Table` node has a normal `renderHTML({ HTMLAttributes })` that merges `this.options.HTMLAttributes` in - the usual way a TipTap node picks up a configured class. But `Table.addProseMirrorPlugins()` only calls that when the table has NO custom NodeView; whenever `resizable: true` AND `editor.isEditable` (true for the live canvas), it registers `prosemirror-tables`' `columnResizing({ View: this.options.View })` instead, and `View` (default `TableView`, exported from `@tiptap/extension-table`) builds its `<table>` with a bare `document.createElement('table')` that never reads `this.options.HTMLAttributes` at all. `Table.configure({ HTMLAttributes: { class: 'doc-table' } })` alone is therefore a no-op on the live editable canvas - confirmed live, the class stayed `""` regardless - even though it correctly reaches the SAME node in any non-editable/non-resizable render path.

Found while wiring up `doc-table`, the class `App\Styles\CssBuilder::tableRules()` scopes its border/zebra/header-shading CSS to (app/Styles/CssBuilder.php): `App\Documents\Render\HtmlRenderer::renderTable()` already emitted it correctly server-side (print/export/share), but nothing in the JS bundle ever put it on a live table, so DocumentStyle's table tokens were invisible while editing. Fixed with `resources/js/editor/extensions/table.js`'s `DocTableView`, a `TableView` subclass that calls `super()` then adds the class to `this.table`, passed as `Table.configure({ resizable: true, View: DocTableView, HTMLAttributes: {...} })` - the `HTMLAttributes` stays too, as a defensive no-cost fallback for any future non-resizable/non-editable path. The general lesson: a TipTap node with a custom `View` (any node, not just tables) needs its class/attributes applied INSIDE that view, never assumed to flow through `HTMLAttributes` just because the node also defines a normal `renderHTML()`.

## A pagination view mode that "replaces the canvas" must mount inside `.canvas`, not beside it
`resources/css/paper.css`'s `.canvas` (the flex wrapper `.paper` sits inside) is `min-height:100%` unconditionally - that rule has nothing to do with `.paper`'s own visibility, so `.canvas` stays a full-viewport-tall EMPTY box the instant `.editor-main.dotdoc-mode-X .paper{display:none}` hides its only real content. Task 8's live browser verification (not catchable by any unit test, since it needs real layout geometry) found `viewModes.js`'s `applyMode()` mounting the Print Preview iframe AND the Multi-Page grid as siblings of `.canvas` (both appended directly to `canvasEl`/`.editor-main`) - which landed both of them below that still-full-height empty `.canvas`, off-screen below the fold on any document taller than one viewport. Both existed since Task 7; neither was ever visible in a real browser before this. The fix (now in place) is `canvasEl.querySelector('.canvas') || canvasEl` as the mount target for anything meant to REPLACE `.paper` - any FUTURE mode that hides `.paper` and shows something else must mount that something-else the same way, and also give it `width:100%` (`.canvas` is `display:flex`, so an unsized child collapses to its own min-content instead of the canvas's available width - `.dotdoc-multi-page-grid{width:100%}` is the existing example).

## A cloned `.paper` needs its OWN background/ink rule - it cannot rely on inheriting one
`viewModes.js`'s thumbnail/multi-page previews clone content into a wrapper (`.dotdoc-thumbnail-inner`) that ALSO carries the `paper` class, so Document Style rules apply to the cloned content - but a clone mounted in the thumbnails RAIL sits outside `.canvas` entirely, so `.canvas .paper`'s (`paper.css`) `background:var(--paper);color:var(--paper-ink)` base rule never reaches it, and neither does `CssBuilder`'s own `.paper{background:#fff}` fallback once something more specific is present. Confirmed via live browser inspection in dark mode (Task 8): a `.paper`-classed clone with no explicit background of its own inherits the dark chrome behind it.

**Fixed:** `.dotdoc-thumbnail .dotdoc-thumbnail-inner.paper{background:var(--paper);color:var(--paper-ink)}` in `CssBuilder::paginationRule()`. Deliberately scoped to the thumbnail's own internal structure (`.dotdoc-thumbnail > .dotdoc-thumbnail-inner.paper`, the same DOM shape `renderThumbnail()` produces everywhere it's called) rather than to `.editor-main` - that is what makes ONE rule reach both the grid's thumbnails and the rail's identically, without needing two separate fixes for two different ancestor contexts. The general lesson: a clone that borrows a Document Style class for STYLING purposes needs its own background/ink declaration wherever its ancestor chain could plausibly make that class's background rule resolve to something other than an actual page, rather than assuming the rule that colours the REAL canvas will reach a clone the same way.

## The live canvas `.paper` must keep its OWN background at all times - never make it transparent to show a gap through it
An earlier version of `paginationRule()` made `.paper` itself `background:transparent;box-shadow:none` while paginated, on the theory that the true page-gap decoration (`.dotdoc-page-gap`) needed `.paper` to have no background for `--ground` (the desk behind the paper) to show through where two "pages" meet - then repainted `.paper>*` (every direct child) `#fff` to put the white back on each real content block. That distorted every page, not just the gaps: `.paper`'s own padding (the page's margins) and the space BETWEEN two ordinary children (a paragraph's own `margin-bottom`) are not covered by any `.paper>*` child either, so the WHOLE document rendered as a scatter of disconnected white text blocks on bare canvas - margins included - instead of one continuous A4 sheet. Confirmed live: every screenshot taken of the editor while that rule was in place showed exactly that, reported directly as "it should show as a full A4 page, instead of just text with white backgrounds."

**Fixed** by removing both rules and leaving `.paper` alone: it keeps its ordinary background (`.canvas .paper{background:var(--paper)}`, paper.css) and box-shadow at all times, paginated or not. The `.dotdoc-page-gap`/`.dotdoc-page-shadow` widgets are already OPAQUE, normal-flow children inserted exactly at the computed break point - they interrupt the paper's own continuous background where a break genuinely falls, without needing the whole element to go transparent to make that happen. Confirmed live afterward, including a forced multi-page split: each page renders as one seamless white sheet, and the gap between two pages still shows clearly as a solid `--ground`-coloured band cutting across it. The general lesson: to punch a visual hole at ONE specific point in an otherwise-continuous element, give the thing AT that point an opaque background - don't make the continuous element transparent and try to repaint everything else around the hole.

## Focus mode reaches the shell chrome via `:has()`, and never touches panel state
`.editor-main.dotdoc-mode-focus` cannot hide `.topbar`/`.rail`/`.dock` with an ordinary descendant selector - per .ai/rules/views.md, all three are `.editor-main`'s own ancestor's SIBLINGS inside `.shell` (layouts/app.blade.php's grid: topbar/rail/canvas/dock), several levels above where `CssBuilder::paginationRule()`'s CSS is even injected (editor.blade.php's `<style id="doc-style">`, itself nested inside `#canvas`). The fix is `.shell:has(.editor-main.dotdoc-mode-focus) .topbar,...,.dock{display:none}` - `:has()` is the only pure-CSS way to react, from an ancestor, to a class on a descendant of a DIFFERENT branch of that ancestor's subtree. It deliberately never writes `data-panel-state`/`data-panel-user` (the rail/dock panel-state machine, .ai/rules/views.md's "Collapsed by default" section) - it only ever hides, never opens or closes, so a panel the writer had open before Focus mode stays recorded as open underneath the whole time and simply reappears, unrestored, the moment the mode class is removed. Confirmed live: `data-panel-state` read `"expanded"` before, during (while `display:none`), and after a Focus-mode round trip, for both an expanded and a collapsed starting state.

`.topbar`'s grid ROW is not `auto` sized (`.shell{grid-template-rows: var(--topbar-h) auto minmax(0, 1fr)}`, a fixed 52px first row) the way `.rail`/`.dock`'s COLUMNS are (shell.css's own comment: "A collapsed panel is display:none, which empties its column, which collapses the track to zero") - so `.topbar{display:none}` alone leaves a dead 52px band of bare `--ground` at the top instead of Focus mode's promised "single continuous scroll of prose". The same `:has()` condition also sets `.shell{grid-template-rows:0 auto minmax(0,1fr)}` to collapse that row; confirmed live via `getComputedStyle(shell).gridTemplateRows` before/after.

## A mid-table page-boundary widget is `position:absolute`, never a normal-flow child of `<tbody>`
An UNRESIZED TipTap table (`Table.configure({resizable: true})` with no manual column drag, so no `colwidth` attrs on any cell - the common case) has no explicit width; its rendered column widths come from ordinary CSS auto-layout, driven by whatever content the browser considers part of each row. A NORMAL-FLOW page-boundary widget landing MID-TABLE (`decorations.js`'s `renderBoundaryWidget()`, `.dotdoc-page-boundary` - footer/gap/header bands, `contain:layout`) used to be inserted as a direct, in-flow child of that table's own `<tbody>`, sitting between two `<tr>` siblings - and, being wide (its bands span close to the full page), measurably distorted the table's OWN auto-layout column computation: removing it shrank the table's columns back down, and repeated reflows (each `getBoundingClientRect()` call, each unrelated `view.dispatch()` a table's NodeView re-validates against) could read a DIFFERENT column width each time, drifting with no guaranteed fixed point - confirmed live while first building `resources/js/editor/pagination/decorations.js`'s table-header-repeat feature (design spec §2.2): a version that re-measured and wrote back a "corrected" width on every pass made the reading grow on EVERY edit anywhere in the document, unboundedly, because each write was itself a DOM mutation feeding the next reading.

**Fixed** by removing the widget from the table's layout algorithm entirely, per CSS 2.1 §17.2.1: an out-of-flow (`position:absolute`) child of a table-row-group never gets wrapped in the anonymous row/cell that would otherwise fold it into column-width computation - confirmed live, restoring the table's TRUE, undistorted columns the instant this applies, stable (not merely bounded) across repeated unrelated edits. `.dotdoc-page-boundary.dotdoc-page-boundary-in-table{position:absolute;left:{margin};right:{margin}}` (`CssBuilder::paginationRule()`) is positioned inside `.paper` itself (`resources/css/paper.css`'s `.canvas .paper{position:relative}` - `.paper` beats `.canvas-region`'s own `container-type: inline-size`, .ai/rules/views.md, as the nearest positioned ancestor); `top` is computed PURELY from already-measured geometry (`decorations.js`'s `tableSplitOverlayTopPx()`: the table's own live top, plus `headerHeight` and the summed `rowHeights` up to the split - never by reading another element's current, possibly-not-yet-updated flow position).

Three further pieces this fix needed, all non-obvious:

1. **`left/right:0` is NOT the same as "matches every other boundary's width."** A normal (non-table) boundary is an ordinary in-flow CHILD of `.paper`, so it inherits `.paper`'s own page-margin `padding` (`CssBuilder::paperRule()`) for free, confining it to the content column. But CSS 2.1 §10.3.7 resolves an ABSOLUTELY positioned descendant's `left`/`right` against its containing block's PADDING BOX, which - for `.paper` as the positioned ancestor - spans `.paper`'s full width, margins included. `left:0;right:0` therefore bled the mid-table widget's header/footer band across the ENTIRE page, edge to edge, instead of stopping at the ~560px content column every normal boundary's band respects - confirmed live (its band measured full paper width; a normal boundary's band on the same page measured the content column). Fixed by setting `left`/`right` to the exact same page-margin values `.dotdoc-page-band`'s own padding already uses (`CssBuilder::horizontalMargins()`), so a mid-table split's running header/footer lines up with every other page's, pixel for pixel.

2. **Reserving the vertical space the widget no longer occupies.** Removing it from flow means nothing pushes the table's next row down by the widget's own height any more - `decorations.js`'s `buildTableSplitGapDecorations()` reserves it instead, via a REAL `Decoration.node()` (`padding-bottom`, carried as a `--dotdoc-split-gap` custom property) on every cell of the row immediately before the split. Confirmed live that a RAW DOM write (`element.style.paddingBottom = ...`, or even just `element.classList.add(...)`) on that row gets REVERTED by ProseMirror's own view-tree reconciliation within about one repagination cycle - it treats a document node's DOM as something it owns and silently corrects it back to what the node's schema/decorations say it should be. A `Decoration.node()` is the opposite: it IS part of what ProseMirror itself considers that cell's expected render, so it survives the exact reconciliation that discards a raw write. `measureBlocks()`'s own row-height reading has to subtract this same amount back out via `rowSplitGapPx()` (reading the same custom property), or a later pass would treat the synthetic gap as real row content and feed a wrong height into `computeBreaks()`.

3. **A `Decoration.widget()` at a fixed KEY does not track a moving target.** Once the widget's position is an explicit, JS-computed `top` (rather than something the browser keeps in sync for free via normal flow), THAT computed value has to be part of the decoration's key, or ProseMirror will happily reuse a stale cached widget - with its stale `top` - whenever the key doesn't happen to differ, discarding whatever fresh `top` this pass just computed. Confirmed live: editing content BEFORE the table (shifting the table's own position on the page) left the widget rendered ~28px off from where the split actually fell, because neither the header text nor blockIndex/offset/pageCount happened to change from that edit. `repaginate()` folds the computed `overlayTopPx` directly into the key to close this.

Also: `measureOverlayHeight()` (which measures the widget's natural height before deciding how much space to reserve) must insert its probe element as a descendant of `.paper` itself, never `document.body` - `.dotdoc-page-band`'s font-size/colour read CSS custom properties (`--doc-size-small`, `--doc-muted`, ...) declared ON `.paper` by `CssBuilder::paperRule()`, a document-style token, not a `:root` global; measuring outside `.paper` entirely left them undefined, silently producing a WRONG height that didn't match the same content rendered for real moments later.

## A newer document over unsaved typing is MERGED block by block; the notice is for a merge that cannot be done
Phase 2 of co-editing (`docs/superpowers/specs/2026-10-16-coediting-phase-2-paragraph-merge-design.md`). A server document that arrives while the tab holds unsaved typing, whether by the poll (`engineHost().onConflict`) or after a save was refused as stale (`saveAnswered()` -> `beginMerge()`), goes to `mergeOrConflict()` in `sync/host.js`, which merges it with `handle.merge()` (`mergeDocuments()` in `sync/merge.js`, pure, run under `node --test` with `tests/fixtures/merge/*.json`), applies the merged document with `applyRemote(merged, {force: true})` and saves it on the new base. The merge matches TOP-LEVEL blocks by id against the base (the document of the version the typing is based on) and decides each block on its own: a block only one side changed takes that side; a block both changed takes THEIRS and mine is offered back (owner decision D1: the later saver loses that block only, on every round); a block they deleted while I typed in it goes and my words are offered back with up to five preceding ids as its place (D2); a block I deleted that they edited goes too and the save carries `overwrite`, so `DocumentStore::save()` keeps their version in the history first (case c2; they are not told, Q1; the label is "Before <name> kept their version", Q2). Characters inside one block are NOT merged, and a list, table, columns block, callout or figure is one block: the loser's whole table is offered back. Nothing is compared as JSON: every input is parsed twice through the schema, a compare copy with the server-stamped `toc.entries`/`crossRef.label` blanked and `[]` levelled to `{}` (the `DERIVED` table, duplicated from `derived.js`; `tests/js/derived.test.js` holds the two identical), and an output copy with the stamps kept. The order is theirs unless only I moved blocks; an inserted block is anchored after its nearest preceding block that is on the page, first when it had no predecessor, LAST when every predecessor is gone (a typist's paragraph lands after an imported document, not before its title). This editor's own trailing paragraph (TrailingNode) is carried into both the merged document and `theirs`, so a merge in which nothing of mine survived still leaves `confirmed` equal to what the editor serialises and `settleIfBackAtConfirmed()` reachable. When each side deleted what the other kept and no block is left, the merge is one empty paragraph under the id of the last block of mine that is NOT in the lost row (none when every block of mine is offered back: the editor assigns one on apply, as UniqueID does; `doc` is `block+`; two deletions are a merge, not the notice). The carried trailing paragraph is checked against the ids of theirs at any depth, as apply.js does. A parse throw, a top-level block without an id, two blocks sharing one, or a merged document that fails `check()` make the merge impossible: `null`, and today's notice, whose sentence now says the two could not be combined. A lost entry's `json` is a plain copy (`Node.toJSON()` builds `attrs` with `Object.create(null)`, which strict `deepEqual`, IndexedDB and Alpine all treat differently from a plain object); `doc.attrs` are compared as JSON strings, so `vars` with the same keys in another order count as mine's change (one extra save, nothing lost). A block whose id the server re-stamps, or that TipTap re-ids on a block conversion, looks like delete + insert. `tests/js/sync.merge.editor.test.js` pins which conversions do: `toggleHeading` and `toggleCodeBlock` keep the id; wrapping a paragraph in a bullet list, ordered list, task list or quote gives the wrapper a new top-level id (the paragraph id moves inside it). So a saved edit to a paragraph that somebody else then wraps is dropped from the page (case c2: kept in the history, nobody told), and a typist in a paragraph somebody else wraps is told it was removed. `applyRemote()` applies block by block only up to `MAX_BLOCK_STEPS` (500) steps; a document-sized change takes the one range of Phase 1.

The loop is bounded and holds while a merge is under way. A save refused as stale (`result.conflict && result.version > baseVersion`) sets `resave` (the text is still owed) and, unless the notice stands or `mergeAttempts` has reached `MERGE_ATTEMPTS` (5; the spec's 3 let three writers in three different paragraphs reach the notice with every merge possible), counts one attempt and calls `beginMerge()`, which does nothing fail-closed, merges the engine's pending document at once when it is new enough, and otherwise DROPS a pending document older than the refused version (`engine.takeRemote()`: left there, the `retry()` after the answered save would merge it, end `merging` and send on a base known to be stale), sets `merging = {version, since}` and `refetch()`es (not `poke()`: the engine may have SEEN that version). While `merging` is set `persist()` sends nothing (`resave = true`; a save on a base known to be stale is churn), `syncState()` stays `dirty`, and the engine's `onPolled` tick calls `expireMerging()` before `resendIfOwed()`: a fetch unanswered for `MERGE_FETCH_EXPIRY_MS` (15 s) ends in the notice, and the owed save goes out after the writer's choice. It runs from the tick and not from `resendIfOwed()` because `onMembers()` (and `resendIfOwed()` with it) runs BEFORE the same poll delivers its document: a poll that brings the awaited document late must be merged, not answered with the notice. An accepted save, `applyFromSync()` and a merge that leaves nothing of mine to save (`changed` false: a follow in disguise, the echo case) reset the count; an OK answer for a version at or above `merging.version` ends the merge too (`saveAnswered()`: a late answer of a save given up on, arriving while the fetch is out, names the very version `engine.saved()` marks as seen, so the fetch would never be delivered); `enterConflict()` clears `merging` and the count and drops a pending engine document OLDER than the version the notice names (`engine.takeRemote()`, then it refetches: Load theirs must show the version the notice names, not one the head has moved past); `adoptVersion()` ends a merge at or below the adopted version as it ends a conflict. On a 200 poll the engine runs `onMembers()` (and with it `resendIfOwed()`) BEFORE it delivers the document, so a save given up on at 15 s goes out again on its old base first and the merge happens on that resend's refusal, with the held document in hand. `mergeOrConflict()` itself does nothing fail-closed, updates the notice without merging while one stands (nothing is merged behind a writer who is choosing), waits while a save is in the air, and takes as its base `confirmed` or, when that is null (a lost answer, a failed request), `known` IF `known.version === baseVersion`: after Keep mine the base names a version the editor never held, there is no base, and the notice stands until a save is accepted (a stated limit). `known` (`{version, json}`) is the last server document this tab held and is NEVER nulled: `markConfirmed(json, version)` sets `confirmed`, `known` and clears `unanswered`, from `opened()`, an accepted save, `applyFromSync()`, `applySuggestion()` and the merge (`theirs` as this editor serialises it when something of mine survived, the editor's own serialisation when nothing did); `confirmed = null` stays a direct assignment where it was. `adoptVersion()` after this page's own restyle moves `known.version` with the base only when `known` was current (a restyle changes stamps, which the levelling absorbs). The echo: `persist()` records `sentSnapshot`; a save given up on (`saveInTheAir()`) or whose request failed sets `unanswered = sentSnapshot`, and a request that FAILED (the Livewire call rejected; a refusal is an answer and does not) also sets `resave`, so the next completed poll tick resends it, because the unload beacon does not carry a document the bundle already counted as sent; the merge takes it as `echo`, and wherever theirs agrees with the echo that block's base is theirs, so a tab recognises its OWN stored save and typing on top of it is kept (this closes the Phase 1 limit "a save whose answer is lost raises the notice against itself"); somebody else's edit of that block after the echo is an honest D1. `overwriteOwed` is ORed with the merge's `overwrites`, never assigned, while something of mine is left to save: an overwrite owed from Put it back or from an earlier c2 merge survives a merge that owes none but still has something of mine to save, until a save that carried it is accepted; a merge that leaves nothing of mine to save (`changed` false) clears it, because no save is left to carry it (the draft merge and the suggestion merge follow the same rule). Every path that owes an overwrite (Keep mine, Put it back, a merge or a suggestion merge whose `overwrites` is true) goes through `oweOverwrite()`, which also records `overwriteFloor`, the base the overwrite FIRST became owed on (set only when none was owed already). Whatever writes the overwrite off clears both, and a Put it back that cannot put the text in restores both as it found them. `draftStamp()` stamps a draft written while an overwrite is owed `Math.min(baseVersion, overwriteFloor ?? baseVersion) - 1`, not simply one below the base: an owed-overwrite draft is set aside on reopen and never merged against a base row written while the overwrite was owed (the failure walk found the other way: seed 11393 with three tabs lost another writer's words). Only a plain Keep mine, with no overwrite owed before it, stamps one below the moved-up base, and its draft is merged on reopen when that is the version of the base row the tab holds. A Put it back pressed after a flagged save left keeps its own overwrite: `putBack()` stamps `putBackSeq = saveSeq` and `persist()` passes `overwrite && putBackSeq < seq` to `saveAnswered()`, so only a save sent AFTER the put-back settles it (declare `putBackSeq` in the Blade: `undefined < n` is false, and the overwrite would be owed for ever). `syncState()` is `busy` while `handle.composing` (an IME composition): nothing is applied under one.

What a merge could not keep goes to the notice bar's lost row (`offerLost()`): entries `{key, id, type, reason: both|deleted, source: merge|draft|suggestion|parked, json, anchors, version, sentence, excerpt}` are APPENDED to `view.lost`, never replaced or coalesced per id (the only entry skipped is an exact duplicate: same id, identical json), so two losses of one paragraph in a row keep both offered versions (the D1 ping-pong); the WHOLE list is parked under `lost-<uuid>` (`parkLost()`), its own key, never the `stale-` slot Load theirs uses. `putBackLost(index, {focus})` puts an entry back through `handle.insertBlock()` (the editor takes focus only when `focus` is true, which the Blade handlers pass as `$event.detail === 0`, a press from the keyboard: after a tap focusing the paper brings up a phone's on-screen keyboard and scrolls; `focusAfterInsert()` in `sync/insert.js` is the one place that decides; the caret is placed either way) (`insertBlockTransaction()` in `sync/insert.js`: after the first of its anchors that is on the page, `insertionPoint()` in `narrow.js`, else the end, else the start; a `both` block with a FRESH id below the winner, a `deleted` block with its OWN id where it was, so comments and cross-references on it come back; nested ids follow the same rule; the caret goes to the end of a block with content, and after an atom, such as a rule, a page break, a section break or a contents list, to the start of the next text block, else the end of the one before, never ON the atom, where the first keystroke would replace it: `caretAfterInsert()`) as an ordinary undoable edit that fires `update` and is autosaved on the current base with NO overwrite flag (it replaces nothing); the entry goes and the park is rewritten with the rest. `putBackAllLost()` walks oldest first and stops at the first failure, which stays listed with `syncNotice = 'Your text could not be put back.'`. `dismissLost()` is async and always asks (`DISMISS_LOST_QUESTION`: every entry is on the page nowhere). It writes the `lost-` park FIRST (`parkLost()` resolves false when the write failed or the browser keeps no drafts) and empties the row only once that write is known to have stored the list; then `markLostDismissed()` stamps the park `dismissedAt` and moves the entries to the row's `dismissed` list, which every later `parkLost()` carries over while it rewrites `entries`, so the text the button promised "kept only in this browser, for 7 days" survives the next loss and is never offered again. When the write failed, every entry stays on the page and `syncNotice` says so (`DISMISS_LOST_FAILED_NOTICE`). That notice is also the memory of the failure: the NEXT press asks a second question (`DISMISS_LOST_UNKEPT_QUESTION`), a yes drops the text with no copy and a no changes nothing. A list that changed while the write was in flight dismisses nothing and says so (`DISMISS_LOST_CHANGED_NOTICE`), because the new entry is not in that copy; an empty list is not a change (an earlier press has already dismissed those entries). It is NOT fail-closed-gated, like `discardSetAside()`. `restoreDraft()` re-offers a park's `entries` when the row was not dismissed, with `source: 'parked'` and the sentence prefixed "From your last visit: ", and does so BEFORE the draft logic: `offerLost()` parks the whole list, so a draft merge's losses are appended after the re-offered ones with their own source, and an earlier visit's park is read before anything overwrites it. Two tabs of one browser share the park (keyed per document, as drafts are). The row is five STATIC item slots switched with `hidden` (`LOST_ROWS = 5` in `host.js`, mirrored by the markup), never `x-for` (`.ai/rules/livewire.md`).

Drafts remember their base. `base-<uuid>` (`saveBase()`/`loadBase()` in `offline.js`) holds `confirmed` with its version, written by `markConfirmed()` and by `adoptVersion()` (both through `writeBase()`), never per keystroke, and by `restoreDraft()` AFTER the draft check (`opened()` passes `writeRow: false`): a draft the document has moved past is merged against the row of ITS version, which the page must read before it writes its own. `restoreDraftIfRestorable()` calls `mergeDraft()` first in the stale branch: with a row of the draft's version, `handle.merge(base, pageDocument, {mine: draft, deletionsWin: false})`; no change and no loss clears the draft without a question (the beacon stored it, or it is all in the document); otherwise `DRAFT_MERGE_QUESTION`, and on yes the pre-merge copy is parked as `stale-` as today, the merge is made AGAIN from the editor as it is after the question and the park (the page is editable meanwhile: applying the first merge wiped what the writer typed in that gap), the merged document applied, losses offered with the `draft` sentences, and what survived saved on the first tick (the word says Editing until then: `opened()` said Saved a moment before). `unsaved` is never lowered there (`view.unsaved || result.changed`) and the tick is owed it (`resave`): the apply empties the editor's own autosave. Load theirs parks the same way, again and again until the editor holds what was parked, so typing during the park is parked too. `deletionsWin: false` because D2 was decided for live co-typing: a days-old draft's deletion of a block somebody changed since does not win and owes no overwrite. No row (an older build, or swept after 7 days), a merge that cannot be done, or a declined question fall to today's park and set-aside. The sweep (`parkedRowIsExpired()`) expires `stale-`, `lost-` and `base-` rows alike and never a live draft. An accepted suggestion over unsaved typing is merged the same way (`mergeSuggestion()`, source `suggestion`), and when it cannot be the typing is set aside first (`setAsideTyping()`), never replaced silently. `applySuggestion()` captures the typing ONCE, before it calls `mergeSuggestion()`: the merge's apply can throw after the editor has changed, and the fall-through must set aside (or, with a text already set aside, put back) the typing and not whatever the page shows by then; the typing is set aside only once the forced apply has gone in. Whatever save is in the air is given up on first (its older document must not become the echo of the next merge, nor its OK answer move the base back); and when a text is ALREADY set aside, an unmergeable suggestion is not put over the typing at all (the suggestion IS stored as a version already, accepting it saved it; `aiError` asks the writer to settle the standing text first, the other tabs still receive it through the poll, and this tab meets it as the notice; if the merge's apply had thrown after changing the editor, the typing is put back first), because the page offers one set-aside text at a time (`setAside`), and replacing the offer would leave the earlier text recoverable only by hand (its park is kept, under a suffixed key, for 7 days, but nothing in the page offers it). Load theirs asks (`LOAD_THEIRS_REPLACES_QUESTION`) before it replaces a text that is already set aside, for the same reason. A restore or an import is merged like any remote document (decision 13: no replacement heuristic). Every new path that writes into the editor carries the fail-closed gate (`.ai/rules/livewire.md`). The server changed nothing: no endpoint, no column, no dependency, `PROTOCOL` stays 1; the only `app/` change was deleting the dead `version-restored` dispatch. `tests/js/sync.merge.walk.test.js` walks two and three tabs through 200 seeded random steps (the failure walk 250, `ADV_STEPS`) and checks convergence, no silent loss, unique ids, no notice, nothing owed and kept heads; `WALK_SEED=<n>` replays a seed and `WALK_SEEDS=<n>` runs seeds 1 to n. `tests/js/sync.merge.walk.failures.test.js` repeats it with the failures of section 11 switched on (lost and late save answers, failed requests and polls, the clock past the 15 s expiries, composition, restores and imports, accepted suggestions, tabs that die over a draft, individual Put it back, a browser without drafts; `ADV_SEED`, `ADV_TABS`, `ADV_SEEDS`, `ADV_FEATURES`); a change to the loop is not done until both walks are green.

The lost row's notices (`PUT_BACK_FAILED_NOTICE`, `DISMISS_LOST_FAILED_NOTICE`, `DISMISS_LOST_CHANGED_NOTICE`) share `syncNotice` with the stop reasons (signed out, no access, gone) and the refused-version notice. They are written only over an empty notice or one of themselves (`setLostNotice()`), never over a stop reason, and cleared (`clearLostNotices()`, only these three) when the list changes or empties or the next Put it back works; a stale failed-copy notice would otherwise make the next Dismiss skip the write for entries never tried, because that notice is also the memory of the failure: the press after it asks `DISMISS_LOST_UNKEPT_QUESTION` and, on yes, dismisses without a copy and stamps an earlier stored list dismissed (best effort), so it does not come back after a reload. The lost-row header does not promise a copy in the browser (the write can fail and is not reported by `offerLost()`); the Dismiss question and title say it where the browser keeps drafts.

Three limits of the first Phase 2 build are closed (spec section 19), each by a rule that is now tested:
- **A gap of versions owes the overwrite.** A merge (live, draft or suggestion) built on a base more than one version older than the document it merges into cannot tell a block that was changed and changed back from one nobody touched, so a deletion of it read as a plain c1 and carried no flag. `owesOverwrite()` in `sync/host.js` (not merge.js, which stays pure) is true when the merge says so itself or when `theirsVersion - baseVersion > 1` and the merged result no longer holds a top-level block theirs holds; the merge then calls `oweOverwrite()` and the save carries the flag, so the server keeps the replaced version in the history. A gap of exactly one version does not (nothing can have been changed back in it). Cost: an extra history row in the gap case. The failure walk has no excuse for it any more (seed 42519 passes on the product).
- **Each tab writes its own lost row.** `lost-<uuid>@<tabId>` (`parkLost(uuid, entries, baseVersion, tabId)`, `markLostDismissed(uuid, tabId)`), never the plain `lost-<uuid>` (an older build's row is still read). On open `reofferLost()` calls `adoptLost(uuid, tabId)`: every row of the document (every earlier tab's, and a plain one) moves into this tab's row and the others are deleted in ONE transaction, so each entry has one owner; exact duplicates are kept once. A tab that is still open keeps writing its own row (recreated if an adopting tab deleted it), so after an adoption an entry can sit in two rows until the next reload, which keeps it once. `unionLostRows()` is pure. `tests/js/offline.idb.test.js` runs offline.js against a small fake IndexedDB (`tests/js/support/fakeIndexedDb.js`). `markLostDismissed(uuid, tabId, listed)` marks the dismissed entries in EVERY row of the document in its transaction (`dismissInRows()`: the tab's own row wholly, other rows by identity, from the tab's row and the list its page showed), so a tab whose row was adopted still dismisses for good; an entry one tab PUT BACK is removed only from that tab's row, so it can be offered once more after a reload from the other row, and putting it back again duplicates the block (nothing is lost; stated limit). A walk with two tabs sharing one browser is not built: the live draft and the base row are shared per document, which the walk model does not represent.
- **Kept parks of set-aside texts are offered one after another.** A park made because the page SET A TEXT ASIDE (Load theirs, an accepted suggestion that cannot be merged, a stale draft set aside at open) is stored with `offerable: true` (`parkStaleDraft(uuid, json, baseVersion, {offerable})`); the pre-merge copy of a draft merge and a declined restore are not. `Put it back` and `Discard` mark every park holding the dealt-with text `resolved` (`resolveParked()`, by content; the rows stay for their 7 days) and then `offerNextPark()` offers the newest park that is offerable and not resolved (`nextParkToOffer()`, `chooseNextPark()`), as a draft from an earlier visit (so Put it back asks its usual questions); it runs once at page open too, after the draft logic. A text from the queue keeps the label its park had (`from`: 'conflict' for Load theirs and an unmergeable suggestion, 'draft' for a stale draft) and has `setAsideBase` null, so Put it back asks and Discard always asks `DISCARD_QUESTION`. It is not offered while `conflict`, `merging` or a stop reason stands: the offer is held in `parkOfferPending` (declared in the Blade) and made on the `onPolled` tick after they clear. Discard offers nothing next when `resolveParked()` could not write (it would offer the same text straight back). The merged draft is stamped with `draftStamp()`. It never replaces a text on offer (checked before and after the store is read), never offers a text the page already shows (it is resolved instead), and the earlier states of typing that Load theirs parked more than once are resolved so they do not come back. The rows are not promoted to the plain key: the flags make the order and the one-time offer explicit without moving rows.

A save whose REQUEST keeps failing (the Livewire call rejects: no answer from the application, e.g. a 413 or a 500 for this document) is resent with a growing hold, not at poll pace for ever. The page counts the failures in a row in `saveFailures` and holds the next send until `saveRetryAt` (both declared in the Blade; this module holds no state): the first failure is resent at the next poll tick as before, then the holds are 5, 10, 20 and 40 s, then 60 s at most (`SAVE_RETRY_DELAYS_MS`, on the clock the 15 s expiries use). `persist()` holds a non-forced send while the hold stands (`resave` stays set, the word stays Not saved, the draft keeps the text) and the first poll tick at or after the hold sends the NEWEST text, so a send is at most one poll interval later than the hold; a keystroke does not bypass it. Any answer to a save, accepted or refused (a late answer of a save given up on too), resets the count; Keep mine (`force`) is never held; one tab's hold does not touch another's. The unload beacon is unchanged: the bundle counts a handed-over document as sent, so a held text is carried by the draft, as before the hold. The failure walk's quiesce moves its clock past the cap. Whether Livewire raises its own error for each failed request was not checked; there are now at most a handful an hour per document.

Known limits of Phase 2 (stated, not fixed):
- Two tabs of one browser: a second tab can be offered a set-aside text that a LIVE first tab is still showing (parks are per browser, not per tab); it asks before it discards or puts it back, and the first tab still shows it. After an adoption an entry can sit in two lost rows until the next reload.
- Pressing Enter in the middle of a paragraph that somebody else changes at the same moment can store the words after the split twice: the new block the split made is kept as mine's insertion, while the paragraph itself is offered back (or lost). Joining two paragraphs (Backspace at the start of one) has the mirror effect: the joined paragraph's words survive only in the lost row. Nothing is lost; the writer sees a duplicate or a lost-row item and deletes or puts back.
- The echo is not applied to block ORDER. After a stored-but-unanswered save that moved blocks, a later move of the same tab can be undone silently by the order comparison against the base.
- An accepted suggestion that retires a save in the air sets no echo (`unanswered`), so the tab's own stored words can come back from a later merge as a lost-row offer. Nothing is lost.
- A block id that comes out twice, nested, in a merged document is not refused (the check is top-level); the editor's repair plugin gives one copy a fresh id on apply.
- The echo rule remembers ONE snapshot (`unanswered`). When two sends in a row both go unanswered and the first was stored, the tab's own words come back from the merge as a lost-row offer. Nothing is lost (Put it back, or Dismiss), but the tab is told about text that is its own.

## A read only editor never writes: not a keystroke, not a command, not a save, not a draft - and it still follows
A person who may read a document and not change it (`DocumentPolicy::update()` false, `.ai/rules/app.md`) is given the editor with `editable: false` (the x-data literal, passed to `mount({editable})`), so TipTap is not editable from the first frame. That is not enough on its own: `editor.setEditable(false)` only stops TYPING, and every TipTap command (the bubble toolbar, the palette, voice text, an AI result, a dropped file) still dispatches. So four things hold the line, each tested: (1) `extensions/readOnlyGuard.js` refuses every transaction that changes the document while `editor.options.editable === false`, except while `allowDocChanges()` runs applyRemote()'s dispatch (a flag, not a meta: `filterTransaction` is asked about the transactions other plugins append before they are tagged as appended). (2) The handle: `readOnly` (getter) and `makeReadOnly()`; `onUpdate`, `flushSave()`, `applyHtml()`, `insertBlock()` and `uploadImage()` do nothing in it. `autosaves` stays TRUE: that flag is fail-closed (an editor holding something that is NOT the document, which must not even take in other people's saves), and a read only editor shows the real document and follows it. (3) `registry.run()` refuses every command not marked `readOnlySafe` on a non-editable editor, and `paletteCommands({readOnly})` lists only those: the exports, search, open another document, the assistant's passes (they only READ, `AiAssistant::runAi()` asks view access; Accept is the write and is drawn only for people who may update) and comment. (4) `sync/host.js`: `readOnly(handle)` is `view.editable === false || handle.readOnly`, and `cannotWrite(handle)` (no editor, fail-closed or read only) replaces the old fail-closed test on EVERY path that writes (persist, resendIfOwed, clearDraftIfSettled, writeBase, edited, the merge and its fetch, keepMine, loadTheirs, putBack, the lost-row put-backs, offerNextPark, restoreDraft); `applyFromSync()` and `syncState()` keep asking about fail-closed alone, so the page follows, and applyFromSync() leaves the draft store alone on a read only page (a draft in this browser may be text typed when this person could still edit). A new path that writes into the editor, a draft or the server asks `cannotWrite()` with a test; a new path that only reads does not. The words: `opened()` reports `Read only` in the idle tone (fail-closed is the danger-toned `Read only`), nothing reports Editing, Saving, Saved or Not saved, and a stop reason says `Not updating` (a signed-out reader is told to reload to sign in again, not to keep editing).

A refused save turns an editing page into this page, but only once the server confirms. `saveContent()` answers 403 to somebody whose role was lowered while the page was open, and a 403 alone does not say why: it is also what a request answers when ANOTHER action sent in it was refused (a Move beside an autosave, the save may even have been stored) and what a firewall in front of the application answers. So `saveRefused(403)` is provisional: it parks the unsent words, holds saves (`accessCheckSince`, `accessBeingChecked()`, honoured by `persist()`, which `resendIfOwed()` reaches, ending with the save wait `SAVE_EXPIRY_MS` if the answer never comes), lets go of the save in the air as owed and possibly stored (`confirmed` null, `unanswered` the snapshot, so the ordinary stale-refusal and echo rules settle a save that was stored), and asks `Editor::canEdit()`. Only an answer of false calls `lockReadOnly()`; true releases the hold and sends the text again; an answer that fails counts as a failed request (back-off). A late answer to a replaced question is ignored (the check carries a token). Livewire's promise for a refused request never settles and Livewire would lay its error page over the document, so the page hooks the request (`window.Livewire.hook('request')` in `init()`, owner object only, taken off in `destroy()`): `isSaveRequest(payload)` says whether it carried `saveContent`, and `saveRefused(status)` (only 403) sets `view.editable = false`, `handle.makeReadOnly()`, lets go of the save in the air, `resave`, `unsaved`, the conflict and the merge, reports `Read only`, re-renders the page (`env.refreshPresence()`, so the server-drawn controls follow) and returns true, which makes the hook `preventDefault()` the error page. `lockReadOnly()` also takes away the lost row and the set-aside row (their buttons would write into an editor that is no longer editable; the text stays parked in this browser, and `unsentKept` says so). A re-render that draws `editable: false` while the editor was mounted editable is handled in `init()` before the `owns` check (`handle.makeReadOnly()`, then a `dotdoc:read-only` window event that the owning object turns into `readOnlyNoticed()`, because a later object's fields are not the ones the bar reads). The words typed since the last stored save are PARKED (`parkStaleDraft(..., {offerable: false, from: 'refused'})`: a copy for recovery by hand, 7 days, not offered, because this page cannot write it back) and the draft is left as it is, which is what an access removed outright does; `view.unsentKept` adds the second sentence to the notice. The notice bar's read only row (`x-bind:hidden="editable || !!syncNotice"`) is static markup like the rest of the bar. Known and not done: a downgrade nobody saves through is noticed only on the next render or save (the poll does not carry the role).
