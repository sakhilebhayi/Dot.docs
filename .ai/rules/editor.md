# Editor

## Editor bundle mirrors DocumentSchema; block ids are 8-char base62
Every TipTap node name and attribute in resources/js/editor/ is one contract with App\Documents\Schema\DocumentSchema, not a second implementation: heading{level,numbered}, figure{kind}, caption, toc{depth,entries}, crossRef{targetId,kind,label}, pageBreak, sectionBreak{setup}, callout{tone}, columns{count}, column, variable{key}, image, taskList/taskItem and the table nodes. DocumentStore::save() runs DocumentSchema::validate() and rejects an unknown node type or a block without a valid id, so the editor cannot invent either.

Every node in DocumentSchema::BLOCKS carries attrs.id: 8 characters of base62 (/^[0-9A-Za-z]{8}$/), generated by extensions/blockId.js to mirror App\Documents\Schema\BlockId. BLOCK_TYPES in that file must stay in lockstep with DocumentSchema::BLOCKS - a type missing from the list saves without an id and the save throws "Block <type> has no valid id". Inline nodes (crossRef, variable) carry NO id.

Heading and figure numbers are never computed in JS. Editor::outline() (server, style-driven) is the only source: it is seeded into the page as data-outline on the wire:ignored editor host and refreshed through @this.outline() after each save, and outline.js fans it out to the heading-number decorations, the toc node view and every crossRef node view. Renderer-visible attribute names win over library defaults - see extensions/textAlign.js, which renames TextAligns textAlign attr to align because HtmlRenderer reads attrs.align.

## The floating toolbar has a keyboard contract, and every part of it is explicit
"Alt text" is the one command in the product whose entire purpose is accessibility, and `ui/bubble.js`'s toolbar is its only home — so nothing about reaching or operating it may rest on a browser default. Four rules, all of them measured by `tests/js/toolbar.test.js`:

1. **Activation is bound, never inherited.** `bindActivation()` binds `mousedown` (the default must be prevented before the editor loses the selection to the click, which a `click` listener is too late for) AND `keydown` for Enter/Space. It tells the callback WHICH it was: a registry command ends in `chain().focus()`, so a key press would apply one tool and drop the writer back in the paper — focus returns to the button unless the press deliberately moved it into the toolbar (the link and alt-text fields). The two form rows' submit buttons and their inputs get the same treatment through `submitOnKey`, with `preventDefault()` keeping it to ONE submission.
2. **`role="toolbar"` means a roving tabindex.** One tab stop for the whole toolbar; Left/Right move between the visible buttons and wrap, Home/End go to the ends (`rovingMove`). Every button being its own tab stop is not the ARIA pattern and makes a reachable toolbar worse than an unreachable one.
3. **Two routes in, both required.** Tab from the paper reaches it because the toolbar is appended to `<body>` and the top bar is the FIRST element of `.shell` (see .ai/rules/views.md — moving the bar back breaks this). `Alt+F10` / `F10` is the APG route for when something else follows the canvas (the dock, the comment sidebar) and it calls `place()` FIRST, because a selection that has not changed fires no `selectionUpdate` and nothing else would bring a dismissed toolbar back. Escape dismisses it and returns the caret.
4. **A blur into the toolbar is not leaving it.** `blurLeavesToolbar()` reads `relatedTarget` (the only reading available while the blur is in flight) and `toolbarHoldsFocus()` reads `activeElement` once it has settled. Hiding on either is what kept "Alt text" mouse-only even after it answered Enter.

## Every mark in DocumentSchema::MARKS must be registered, or the document opens EMPTY
TipTap's createNodeFromContent SWALLOWS a schema error and returns an empty doc, so one unregistered node or mark turns the whole document into a blank page - and the next keystroke autosaves that blank page over the real content. This is why extensions/textStyle.js exists even though nothing in the UI writes textStyle yet. Two guards, both in index.js mount(): the Editor is built with `enableContentCheck: true` + `onContentError`, and the incoming JSON is also checked against the live schema by the pure `isContentValid(json, {nodes, marks})` in validation.js. Either failing calls failClosed(): read-only, a visible `.dotdoc-content-error` banner, and autosave OFF. Never "fix" a schema mismatch by relaxing that - register the node/mark instead.

## Style-bearing attrs are whitelisted on BOTH sides, and normalised before they persist
paragraph/heading.align, columns.count, image.src and textStyle.color all end up inside a `style` (or `src`) attribute. An Echo payload goes straight to setContent() and NEVER passes through parseHTML, so parseHTML alone is not a guard. resources/js/editor/attrs.js holds the client whitelists (normaliseAlign / alignStyle, normaliseColumnCount 2-4, isValidImageSrc, normaliseColor hex-only, asText for anything handed to a DOM-spec renderer as a text node) and is dependency-free so tests/js can run it under `node --test` (`npm test`). The server mirrors it in HtmlRenderer::alignStyle()/renderColumns() and, so a bad value never persists at all, in DocumentSchema::normalise(), which DocumentStore::create()/save() run right after ensureIds(). Change one side and you must change the other. Block ids from stored JSON also go through dom.js blockSelector() (CSS.escape) before they become a querySelector.

## Remote updates go through applyRemote(), which VALIDATES BEFORE it cancels the pending save
A `.document.updated` Echo payload must reach the editor as `handle.applyRemote(e.json)`, never `editor.commands.setContent()`: applyRemote sets `addToHistory: false` so a colleague's paragraph is not something YOU can undo, passes `errorOnInvalidContent: true` inside try/catch, and restores the caret best-effort. ORDER MATTERS and is the whole point: validate and apply FIRST, and only once the remote document has actually landed clear the debounce timer, drop the dirty flag and set `lastSaved`. Cancelling first (as an earlier version did) throws away the writer's own unflushed keystrokes every time a payload is refused - a refusal must leave the local state, and the armed timer, exactly as they were. Cancelling AFTER a successful apply is still required, or the debounce sends the pre-merge document straight back and clobbers the collaborator.

## The pagehide/destroy flush goes by BEACON, never Livewire
Livewire cannot issue a request during unload at all: its CommitBus defers every `$wire` call on a 5 ms timer that an unloading page never runs, so `$wire.saveContent()` does not even create a request. `flushSave({beacon: true})` (called by the `pagehide` listener and by `destroy()`) instead POSTs `{_token, content}` as an `application/json` Blob through `navigator.sendBeacon()` to `POST /documents/{uuid}/autosave` (`App\Http\Controllers\DocumentAutosaveController`, `['version' => 'none']`, no version snapshot). sendBeacon cannot set headers, so there is no `X-CSRF-TOKEN`; the token rides in the JSON body, which is fine because Laravel's CSRF middleware reads `$request->input('_token')` and `input()` reads the decoded JSON for an application/json request. The beacon's outcome is unknowable from the page, so the offline draft stays as the second safety net.

## Draft recency is decided by VERSION, never by a clock; drafts are cleared only when the save settled
`Editor::saveContent()` returns `['ok' => bool, 'version' => int]` ($wire actions resolve with the return value). `offline.js` `saveDraft(uuid, json, baseVersion)` stores the version the last successful save reported, seeded from `$document->version` at mount; `loadDraft()` returns `{json, savedAt, baseVersion}`. On mount a draft is offered ONLY when `draft.baseVersion === document.version` (nobody has saved since) AND `DotDoc.documentsDiffer(draft, editor.getJSON())` is true - that comparison strips `toc.entries` and `crossRef.label`, the two fields `Outline::apply()` stamps into stored JSON, or every single load would look like a difference. A LOWER baseVersion is not restorable and not this page's to destroy either: it is parked under a `stale-<uuid>` key with a `console.info` explaining why. Do NOT go back to comparing `savedAt` with `updated_at` - those come off two different clocks, and a client running slow discards real offline work.

Clearing a draft is equally strict. After a save resolves with `ok`, the draft is dropped only when `handle.pending` is false AND the editor's current JSON still equals the snapshot string captured when THAT request was sent - saves resolve out of order, and an older one must never delete the only copy of newer keystrokes. A rejected save (`ok: false`) keeps the draft and renders the `content` error in the status area. In fail-closed mode (`handle.autosaves === false`) the bridge does nothing at all: no draft write, no draft read, no clear, no save - what the editor is holding then is not the document.

## Raw HTML enters through applyHtml(), never setContent()
With `enableContentCheck: true`, `editor.commands.setContent(html)` THROWS on a tag this schema does not register, and the throw comes out of an Alpine handler with nothing to catch it. Every raw-HTML path (the AI panels' replace and insert) goes through `handle.applyHtml(html, {mode})`: `generateJSON(html, extensions)`, then `isContentValid()` against the live schema, then `isEmptyDocument()` - `doc` is `block+`, so HTML this schema drops entirely comes back as ONE EMPTY PARAGRAPH, and `content.length === 0` would not catch it, but replacing a real document with it would erase the document. Only then does it apply, with `errorOnInvalidContent: false`, inside try/catch. False leaves the document untouched and shows the error in the status area. An accepted AI suggestion arrives as server-stored JSON and goes through `applyRemote()` for the same reason.

## Every block insert goes through the registry's blockInsert() guard
`resources/js/editor/guards.js` holds `isInCaption()` and `blockInsert()` (dependency-free, exercised by `npm test`). A `caption` is inline-only, so a block inserted there splits the figure from its media. EVERY path that inserts a block passes the guard: the registry entries the palette and slash menu list, the extensions' own keyboard shortcuts (`pageBreak`'s `Mod-Enter`), the image picker and `uploadImage()` in index.js (which re-checks at INSERT time, because the file dialog is asynchronous), and the Blade toolbar buttons - which call `window.DotDoc.run(ed(), 'table')` rather than `ed().chain()...insertTable()`. A toolbar button that reaches for `editor.chain()` directly is a button that can split a figure.

## An asynchronous insert re-runs the caption guard at INSERT time, not at request time
isInCaption() answers for the selection at the moment it is called, which is worthless for anything with an await in it. uploadImage() in index.js goes through a file dialog AND an HTTP request, and the writer can click into a figure caption while either is open - inserting against the selection at that later moment splits the figure (torn caption, phantom image{src:null} figure, orphan image). The rule: capture editor.state.selection.from BEFORE the await, map it forward with an editor.on(transaction) handler for as long as the request is in flight (removed in a finally), and insert with insertContentAt(blockInsertPosition(editor, pos), node) - never setImage()/insertContent(), which both go to the selection. blockInsertPosition() (guards.js, dependency-free, covered by npm test) returns the mapped position, or the position AFTER the enclosing figure when it has drifted inside one, or null when the position will not resolve. A figure is built as one node ({figure, [image, caption]}) rather than image-then-wrapInFigure, because wrapInFigure works off the selection too; focusInsertedCaption() then finds the caption in a bounded scan forward from the insert position.

## A draft that cannot be restored is PARKED, and parked drafts expire after 7 days
Never delete a draft the writer might still want. Two paths park instead of deleting: a draft whose baseVersion is behind the document (somebody saved since), and a draft the writer DECLINED at the restore confirm() - that confirm has no undo behind it, so a mis-click must not destroy the only copy of somebody offline work. Both call window.offlineDraft.parkStaleDraft(uuid, json, baseVersion), which writes the row under stale-<uuid> with a parkedAt stamp and replaces whatever was parked for that document before, and then clearDraft() on the live key. Parked rows are not kept for ever: offline.js purgeStaleDrafts() runs once per app boot from initOfflineSupport() and deletes stale- rows older than STALE_TTL_MS (7 days), dating a row by parkedAt, falling back to savedAt for rows parked by an older build, and sweeping a parked row that carries neither. The decision itself is the pure staleDraftIsExpired(row, now, ttl), covered by npm test; it NEVER expires a live draft row, however old, because age says nothing about whether it is still the only copy of something.

## A pagination view mode that "replaces the canvas" must mount inside `.canvas`, not beside it
`resources/css/paper.css`'s `.canvas` (the flex wrapper `.paper` sits inside) is `min-height:100%` unconditionally - that rule has nothing to do with `.paper`'s own visibility, so `.canvas` stays a full-viewport-tall EMPTY box the instant `.editor-main.dotdoc-mode-X .paper{display:none}` hides its only real content. Task 8's live browser verification (not catchable by any unit test, since it needs real layout geometry) found `viewModes.js`'s `applyMode()` mounting the Print Preview iframe AND the Multi-Page grid as siblings of `.canvas` (both appended directly to `canvasEl`/`.editor-main`) - which landed both of them below that still-full-height empty `.canvas`, off-screen below the fold on any document taller than one viewport. Both existed since Task 7; neither was ever visible in a real browser before this. The fix (now in place) is `canvasEl.querySelector('.canvas') || canvasEl` as the mount target for anything meant to REPLACE `.paper` - any FUTURE mode that hides `.paper` and shows something else must mount that something-else the same way, and also give it `width:100%` (`.canvas` is `display:flex`, so an unsized child collapses to its own min-content instead of the canvas's available width - `.dotdoc-multi-page-grid{width:100%}` is the existing example).

## A cloned `.paper` cannot rely on `.editor-main.dotdoc-paginated .paper{background:transparent}` NOT matching it
`CssBuilder::paginationRule()` sets `.editor-main.dotdoc-paginated .paper{background:transparent;box-shadow:none}` so the LIVE canvas's page-gap decorations can show `--ground` through where two "pages" meet - `.paper>*{background:#fff}` then re-whitens each real content block. `viewModes.js`'s thumbnail/multi-page previews clone content into a wrapper that ALSO carries the `paper` class (so Document Style rules apply to it) - but that wrapper is `.paper`'s own only DIRECT descendant selector's target is `.canvas .paper`/`.paper>*`, and the clone is not a direct child of anything giving it the white re-fill. Confirmed via live browser inspection in dark mode (Task 8): the Multi-Page grid's thumbnails, once correctly positioned on-screen, rendered near-invisible (transparent/dark background, dark ink) because the descendant selector `.editor-main.dotdoc-paginated .paper{background:transparent}` matches the clone too, and nothing overrides it back to white for a THUMBNAIL specifically. Not fixed in Task 8 (a real CSS-specificity fix, not a one-line change, and this task's scope was items 8/9 plus what broke while touching them) - whoever fixes item 3/4/5's thumbnail legibility needs a rule with equal-or-higher specificity than `.editor-main.dotdoc-paginated .paper`, placed AFTER it in `paginationRule()`'s concatenated string, scoped to `.dotdoc-thumbnail-inner.paper` (and possibly the rail's own thumbnails, which sit outside `.canvas`/`.editor-main` entirely and so need `.canvas .paper`'s WHITE rule reaching them some other way too - check both, not just the multi-page grid).
